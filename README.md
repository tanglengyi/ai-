# AI 应用技术 × 业务深度学习路线

> 面向具有 ToB 产品、业务流程与数据梳理经验，希望从“知识库功能产品”升级为“懂技术、懂评测、懂业务结果”的 AI 应用型人才。

最后核验学习链接：**2026-07-24**

## 1. 这份仓库解决什么问题

很多 AI 知识库项目停留在：上传文档、切片、向量检索、调用大模型、生成一个聊天界面。这样的能力容易被平台化工具覆盖，也很难回答客户真正关心的问题：

- 为什么这个方案能解决业务问题？
- 模型为什么答错？
- “准确率”具体指什么，如何测量？
- 应该使用 RAG、微调、工作流还是规则引擎？
- 如何处理版本冲突、权限、时效性、拒答和人工升级？
- 上线后是否真正降低成本、提高效率或改善转化？

本仓库将能力目标定义为：

> **能够把不确定的大模型能力，建设成可测量、可解释、可迭代、可落地的业务系统。**

## 2. 推荐职业定位

结合已有的 ToB 产品、流程再造、字段与数据梳理经验，更适合的发展方向是：

- AI Solutions Product Manager
- Technical Product Manager, AI/LLM
- AI Solution Architect
- AI Application Architect
- Industry AI Solution Manager

建议能力配比：

- **70% AI 应用技术深度**：Python、LLM、RAG、评测、工程化、成本与可观测性。
- **30% 行业业务深度**：业务对象、流程、状态、字段、异常、规则、组织与业务指标。

不必一开始就与算法研究人员竞争预训练和分布式训练，但需要做到：能搭建、能定位问题、能设计实验、能解释结果、能推动业务闭环。

## 3. 总体学习框架

```text
业务问题与目标
    ↓
业务流程、规则、角色、状态、数据对象
    ↓
数据治理与知识建模
    ↓
AI 方案选择：Prompt / Workflow / RAG / Fine-tuning / Agent
    ↓
应用工程：接口、存储、权限、日志、部署、监控
    ↓
评测：检索、生成、系统、业务四层指标
    ↓
上线验证：质量、成本、时延、风险、ROI
    ↓
失败分析与持续迭代
```

学习时始终采用“五步闭环”：

1. **定义**：能够准确解释概念、边界和适用条件。
2. **实现**：亲手写最小代码或完成可运行实验。
3. **对比**：至少比较两种方案，而不是只做一个 Demo。
4. **评测**：使用固定数据集和指标验证差异。
5. **业务化**：说明对业务流程、成本、效率和风险的影响。

## 5. 最终验收标准

完成路线后，应能够独立回答并用实验验证以下问题：

1. 一个业务问题是否真的需要大模型？
2. 为什么选择规则、工作流、RAG、微调或 Agent？
3. 数据应该如何清洗、分块、标注和建模？
4. 检索失败与生成失败如何区分？
5. 如何构建覆盖正常、异常、拒答和版本冲突的评测集？
6. 如何计算检索质量、回答忠实度、任务成功率和人工升级率？
7. 如何在准确率、时延、成本和风险之间做取舍？
8. 如何把一次 Demo 变成可持续迭代的生产系统？
9. 如何向客户解释系统边界、效果、上线风险和 ROI？
10. 如何通过真实项目证明自己的技术深度与业务能力？

## 6. 推荐实践项目

本仓库建议以 **“多语言工业设备售后诊断与知识问答系统”** 作为主线项目：

- 真实业务复杂度高，包含型号、固件、App 版本、错误码、设备状态和环境条件。
- 既能发挥 ToB 流程、数据、规则和字段梳理优势，又能训练 RAG、评测和工程能力。
- 可形成代码、数据模型、评测报告、业务报告和项目复盘，适合求职展示。

详见：[工业设备多语言售后诊断系统项目蓝图](docs/07-industrial-support-project.md)。

## 7. 使用原则

- 优先学习官方课程、官方文档与原始论文。
- 不以“看完课程”为完成标准，以可运行产出和评测报告为标准。
- 不追逐所有新框架，先掌握稳定的底层概念与实验方法。
- 企业数据必须获得授权并完成脱敏；作品集可保留结构，替换真实内容。
- 所有模型、课程、价格和平台能力都可能变化，实际使用前应再次核验官方页面。
