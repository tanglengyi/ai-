# FACTS-E 3.1 升级说明：补齐核心能力总纲

> 基于 [AI 产品经理核心能力总纲](00-ai-product-manager-core-capability-framework.md) 对 FACTS-E 3.0 进行缺口检查和增量升级。

---

## 1. 缺口检查结论

FACTS-E 3.0 已经较完整覆盖：

- AI 需求和业务问题分析；
- RAG、Agent、Workflow、微调、推理和评测；
- 产品基本功、数据分析、商业化、MaaS、ToC、多模态和机器人；
- 交付、验收、续费和规模化。

但与新的能力总纲相比，仍有三个需要提升为一级能力的部分：

1. **上下文工程**：原有内容分散在 Prompt、RAG、Memory、Tool 和多轮对话中，缺少统一框架。
2. **快速原型与实验验证**：原有内容主要停留在 Demo/MVP 和练习要求，缺少明确方法和验收标准。
3. **Agent 选型**：需要更明确地区分 Workflow、单 Agent 和 Multi-Agent，防止把多 Agent 当作默认高级方案。

需求判断和评测已经覆盖较完整，本次主要调整其结构地位：将其与上下文工程共同作为 AI 产品经理三项核心能力。

## 3. 新增专项一：上下文工程面试题

### 3.1 基础题

1. Prompt Engineering 和 Context Engineering 有什么区别？
2. 一个企业 AI 助手的完整上下文由哪些部分组成？
3. System Prompt、用户输入、历史对话、RAG 证据和工具结果如何排序？
4. 上下文越长是否一定越好？
5. 为什么正确文档已经放入上下文，模型仍可能回答错误？
6. Context Window、Token Budget 和 KV Cache 有什么关系？
7. 多轮对话中，哪些信息应该保留，哪些应该摘要或丢弃？
8. 用户画像、长期记忆和业务状态有什么区别？
9. 如何处理上下文中的重复、冲突和过期信息？
10. 如何验证某段上下文是否真正改善效果？

### 3.2 工程题

11. 如何设计 Context Assembly Pipeline？
12. 上下文来源的优先级和可信等级如何定义？
13. 如何给上下文分配 Token 预算？
14. 如何进行历史消息压缩而不丢失关键业务状态？
15. 如何把数据库事实、文档证据和工具结果放入同一次请求？
16. 如何避免 Query Rewrite 把用户未提供的条件写入上下文？
17. 上下文缓存如何处理权限、版本和时效风险？
18. 如何进行 Context Ablation Test？
19. 如何发现 Lost in the Middle 或关键信息被噪声淹没？
20. 如何监控线上上下文长度、命中来源、证据利用率和成本？

### 3.3 安全题

21. Prompt Injection 为什么本质上也是上下文信任边界问题？
22. 如何区分系统指令、可信业务数据和不可信用户内容？
23. 如何防止检索到的恶意文档改变系统行为？
24. 如何保证用户只能访问自己有权限的上下文？
25. 长期记忆错误后，用户如何查看、更正和删除？

### 3.4 上下文工程回答模板

```text
任务：模型要完成什么任务？
来源：需要哪些规则、状态、数据、知识、记忆和工具结果？
权限：每类信息谁可以访问？
组织：以什么顺序和结构进入上下文？
取舍：如何控制长度、噪声、时延和成本？
冲突：不同来源不一致时如何裁决？
维护：如何更新、压缩、失效和删除？
评测：如何通过消融实验和业务指标验证？
```

## 4. 新增专项二：快速原型与实验验证

### 4.1 面试题

1. AI 产品为什么不能只用静态原型验证？
2. 一个 AI Demo 最小需要包含哪些模块？
3. 如何在三天内验证一个 AI 需求？
4. Demo、技术 POC、业务 POC、MVP 和生产系统有什么区别？
5. 如何选择用于原型验证的真实样本？
6. 如何同时比较两个模型、两个 Prompt 或两套 RAG 策略？
7. 快速原型是否必须连接真实业务系统？
8. 如何记录 Prompt、模型、输入、输出、Token、时延和成本？
9. 如何避免只挑简单样本造成 Demo 假成功？
10. 什么结果说明原型应该停止，而不是继续优化？
11. 产品经理需要掌握多少 Python 和 API 能力？
12. 低代码 Agent 平台能否替代基础工程理解？
13. 如何把原型中的硬编码逻辑转成生产配置、规则或服务？
14. 如何在原型阶段验证安全、权限和人工兜底？
15. 如何把原型失败样本转成第一版评测集？

### 4.2 最小原型组成

```text
输入界面
→ Prompt/Workflow
→ 模型 API
→ 可选 RAG/Tool
→ 结构化输出
→ 日志与 Trace
→ 小型评测集
→ 质量/时延/成本对比
```

### 4.3 七天验证流程

| 天数 | 任务 | 产出 |
|---|---|---|
| Day 1 | 明确用户任务、Baseline 和假设 | 一页立项假设 |
| Day 2 | 准备 30–100 条代表性样本 | 小型评测集 |
| Day 3 | 搭建最简单 Baseline | 可运行 Demo |
| Day 4 | 对比第二套方案 | 对比结果 |
| Day 5 | 分析 Bad Case | 错误分类 |
| Day 6 | 验证用户流程和人工兜底 | 交互与流程原型 |
| Day 7 | 输出 Go/No-Go 建议 | 评测和商业判断 |

### 4.4 原型验收标准

- 不是只展示几个成功案例；
- 至少包含一套固定样本；
- 至少比较两种方案；
- 能记录版本、Token、时延和成本；
- 有明确失败样本和边界；
- 能说明从 Demo 到生产还缺什么；
- 能给出继续、调整或停止的判断。

## 5. 新增专项三：Workflow、单 Agent 与 Multi-Agent 选型

### 5.1 选型矩阵

| 方案 | 适用场景 | 优点 | 主要风险 |
|---|---|---|---|
| 规则/Workflow | 路径明确、条件可枚举 | 稳定、可审计、成本可控 | 灵活性较低 |
| 单 Agent | 路径不确定、需要动态选择工具 | 架构相对简单、适应性强 | 可能循环、误用工具 |
| Multi-Agent | 角色目标、权限或并行任务明显不同 | 可分工、并行、互相评审 | 成本、时延、错误传播和调试复杂 |

### 5.2 面试题

1. 什么情况下 Workflow 比 Agent 更合适？
2. 单 Agent 能解决的问题，为什么不要直接使用 Multi-Agent？
3. Multi-Agent 的角色应该按部门、技能还是任务阶段拆分？
4. 多个 Agent 使用同一模型是否仍有价值？
5. Agent 之间通过什么状态和消息协议协作？
6. Agent 输出如何校验后才能传给下一个 Agent？
7. 如何避免多个 Agent 相互确认却没有真实证据？
8. 如何限制总步数、总 Token、总成本和最长执行时间？
9. 如何评估每个 Agent 的贡献，而不是只看最终结果？
10. Multi-Agent 效果提升多少才值得增加复杂度？
11. 什么时候应该把某个 Agent 替换成规则、检索或普通服务？
12. 真实操作前由哪个 Agent 或人工进行最终审批？

### 5.3 选型回答模板

```text
任务是否路径明确？
→ 明确：优先 Workflow
→ 不明确：是否需要动态选工具？
   → 否：普通 Chain/模型调用
   → 是：单 Agent
      → 是否存在明显独立角色、权限隔离或并行收益？
         → 否：保持单 Agent
         → 是：验证 Multi-Agent 的质量增量是否覆盖成本和复杂度
```

## 6. 对 FACTS-E 3.0 的结构调整建议

### 调整一：增加能力总纲入口

在学习和面试前，先阅读：

[AI 产品经理核心能力总纲](00-ai-product-manager-core-capability-framework.md)

### 调整二：三项核心能力作为一级学习顺序

```text
需求判断
→ 产品评测
→ 上下文工程
→ RAG
→ Agentic Workflow
→ 快速原型
→ 产品化
→ 经营与规模化
```

### 调整三：技术题不再按框架名称背诵

每道题使用：

```text
定义
→ 适用条件
→ 实现方式
→ 业务价值
→ 局限和风险
→ 评测验证
```

### 调整四：增加作品集产出

每个 AI 项目除架构图和评测报告外，再增加：

- AI 需求立项判断表；
- Context Assembly 设计图；
- Token 预算表；
- 原型实验记录；
- Workflow/Agent 选型说明；
- Demo→生产差距清单。

4. 如何控制上下文长度、质量、权限和成本？
5. 为什么选 Workflow、单 Agent 或 Multi-Agent？
6. 如何在一周内完成可评测的原型？
7. 原型达到什么标准才值得进入生产化？
8. 如何把 AI 能力转成可交付、可监控和可经营的产品？
