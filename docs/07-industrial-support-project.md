# 07｜多语言工业设备售后诊断系统项目蓝图

## 1. 项目定位

项目名称：**Industrial Support Copilot｜多语言工业设备售后诊断与知识问答系统**

项目目标不是再做一个“上传文档即可聊天”的知识库，而是建设一个能够：

- 识别设备、版本、状态和环境条件。
- 检索适用的产品知识与故障规则。
- 对信息不足的问题主动追问。
- 给出有引用、可执行的排障步骤。
- 对高风险或证据不足问题正确转人工。
- 记录结果并持续进入评测和知识更新闭环。

该项目适合作为 AI 应用技术深度与 ToB 业务深度的综合作品集。

## 2. 业务背景

工业设备售后问题通常具有以下复杂性：

- 同一产品存在多个型号和硬件版本。
- 不同固件、App 和地区的功能存在差异。
- 用户描述口语化，信息经常不完整。
- 同一现象可能由电量、任务、天气、传感器、地图或硬件造成。
- 操作步骤具有顺序和安全要求。
- 资料分散在手册、FAQ、工单、聊天、测试报告和研发说明中。
- 一线客服需要快速回答，但复杂问题仍依赖研发或技术支持。
- 面向多国销售时还涉及翻译、术语一致性和地区差异。

## 3. 目标用户

| 角色 | 需求 | 系统价值 |
|---|---|---|
| 终端客户 | 快速解决常见问题 | 自助排障、减少等待 |
| 一线客服 | 快速获得准确话术和步骤 | 降低查询时间和错误率 |
| 技术支持 | 获得结构化问题信息 | 减少重复询问 |
| 产品/研发 | 了解高频问题与版本缺陷 | 支持产品迭代 |
| 知识管理员 | 管理版本、审核与失效 | 保证知识质量 |
| 管理者 | 查看效率、成本和升级率 | 判断项目 ROI |

## 4. 业务目标示例

正式项目应先采集 Baseline，再确定目标。示例目标：

- 高频问题平均处理时长下降 40%。
- 一线客服首次解决率提升 20 个百分点。
- 重复咨询率下降 20%。
- AI 回答引用有效率达到 95%。
- 高风险问题正确升级率达到 98%。
- 信息不足时的有效追问率达到 90%。

以上数字仅用于项目设计示例，不应作为未测试系统的宣传结果。

## 5. 范围设计

### 5.1 第一阶段纳入范围

- 产品功能说明。
- App 设置指导。
- 建图、切割、回充、雨淋、任务和连接类问题。
- 已标准化错误码。
- 指定型号与固件版本。
- 中文、英语、德语、法语和俄语等多语言输入。
- 客服辅助模式，不直接控制设备。

### 5.2 第一阶段不纳入范围

- 未授权远程控制。
- 可能造成伤害的维修指导。
- 无明确标准的硬件拆机判断。
- 赔付、法律责任和保修争议自动裁决。
- 缺乏证据时给出确定性故障结论。

## 6. AS-IS 现状流程

```text
客户描述问题
→ 客服询问型号/版本/现象
→ 在多个文档和聊天记录中搜索
→ 根据经验判断
→ 回复操作步骤
→ 客户尝试
→ 未解决时再次补充信息
→ 升级技术支持
→ 技术人员重复询问并查日志
→ 给出处理结果
```

典型问题：

- 关键字段收集不完整。
- 文档版本混用。
- 不同客服口径不同。
- 客户语言和内部技术语言不一致。
- 已解决案例没有结构化沉淀。
- 升级工单缺乏上下文。

## 7. TO-BE 目标流程

```text
客户/客服输入问题
→ 语言与意图识别
→ 提取型号、版本、错误码、状态、环境
→ 判断缺失信息并追问
→ 查询实时设备信息（可选）
→ 按权限和版本检索知识
→ 规则引擎判断高风险条件
→ 生成分层诊断和操作步骤
→ 引用来源并说明置信边界
→ 客户反馈是否解决
   ├─ 已解决：记录方案与结果
   └─ 未解决/高风险：生成完整升级信息包
→ 专家处理并修正
→ 审核后更新知识与评测集
```

## 8. 核心用户故事

### 8.1 客服辅助诊断

作为客服，我输入客户的原始描述后，系统自动提取设备信息、提示缺失字段、检索适用知识，并生成可编辑回复，以便快速且一致地处理问题。

### 8.2 多语言回复

作为客服，我希望系统在保留产品术语和操作含义的前提下生成目标语言回复，并同时显示中文内部说明，避免翻译改变技术含义。

### 8.3 高风险升级

作为技术支持，我希望高风险或证据不足的问题自动转人工，并携带完整的设备信息、已执行操作、引用资料和系统不确定点。

### 8.4 知识版本管理

作为知识管理员，我希望每条知识都标记适用型号、固件范围、地区、生效时间和审核状态，过期知识不能进入正式回答。

### 8.5 失败闭环

作为产品或研发人员，我希望查看高频失败问题、人工修改内容和最终解决结果，用于更新产品、知识和评测集。

## 11. RAG 设计

### 11.1 数据准备

文档类型使用不同策略：

- 用户手册：按标题层级 + 父子分块。
- FAQ：一问一答为基本单元。
- 错误码表：结构化存储 + 文本索引。
- 测试报告：按测试项、环境和结论切分。
- 历史工单：只纳入已验证解决案例，并去除个人信息。
- 研发说明：标记内部权限和有效版本。

### 11.2 检索策略

```text
已知型号/版本/地区过滤
→ BM25 召回精确错误码和术语
→ 向量召回语义相似内容
→ RRF 融合
→ Reranker 重排
→ 版本和可信度规则校验
→ Top-K 上下文组装
```

### 11.3 生成原则

答案分为：

1. **判断**：当前最可能属于哪类问题。
2. **依据**：来自哪些设备状态和知识来源。
3. **需要确认**：哪些关键信息仍缺失。
4. **操作步骤**：按顺序给出安全动作。
5. **结果判断**：如何判断是否恢复。
6. **升级条件**：什么情况下停止操作并联系支持。

## 13. 多语言设计

不能只在最后翻译答案，应保留：

- 用户原始语言。
- 内部标准中文/英文术语。
- 目标语言术语表。
- 不翻译字段：型号、错误码、版本和按钮名称。
- 每种语言的评测集。

建议建立术语表：

| 标准术语 | 英语 | 德语 | 法语 | 俄语 | 说明 |
|---|---|---|---|---|---|
| 回充 | Return to charge | Zur Ladestation zurückkehren | Retour à la station | Возврат на зарядку | 统一产品术语 |
| 雨淋延迟 | Rain delay | Regenverzögerung | Délai pluie | Задержка после дождя | App 设置项 |

多语言指标应分别统计，不能只用中文结果代表所有语言。

## 17. 风险控制

### 17.1 错误操作风险

- 高风险规则优先由确定性程序判断。
- 危险操作不由模型自由生成。
- 关键步骤引用正式文档。
- 证据不足时停止诊断并升级。

### 17.2 数据风险

- SN、联系方式和地址脱敏。
- 客户数据按租户隔离。
- 检索前执行权限过滤。
- 日志设置访问权限和保留周期。

### 17.3 知识风险

- 未审核文档不进入正式回答。
- 过期版本自动失效。
- 冲突知识进入人工处理队列。
- 研发临时说明不得直接覆盖正式政策。

### 17.4 模型风险

- 固定模型版本并进行回归测试。
- 设置超时、重试和降级模型。
- 监控输出格式、幻觉和成本漂移。

## 20. 面试陈述示例

> 我没有把项目定义为普通知识库，而是先梳理工业售后中的设备、型号、固件、错误码、任务状态和升级流程。技术上用结构化数据库管理确定性事实，用混合检索和 Reranker 处理文档知识，用规则引擎控制高风险条件，用 LLM 完成问题理解和多语言回复。我建立了覆盖信息不足、版本冲突、拒答和人工升级的 Golden Dataset，并分别测量检索、生成、系统和业务指标。项目重点不是做出聊天页面，而是定位每类错误发生在哪一层，并证明质量改善是否降低客服处理时间和升级率。
