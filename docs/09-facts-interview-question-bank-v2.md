### 0.1 使用资料时的质量规则

这些资料适合“发现面试题”，但不代表所有答案都可以原样背诵。2.0 采用以下规则：

- **题目保留**：高频问题、追问方向和知识边界保留。
- **答案重构**：按“定义 → 原理 → 业务影响 → 权衡 → 评测”重新组织。
- **时效标记**：涉及具体模型、参数规模、框架版本时，面试前应再次核验。
- **不确定性说明**：没有项目数据时，必须说“设计目标”或“实验结果”，不能冒充生产效果。
- **岗位分层**：产品/解决方案岗不要求完整数学推导；算法岗需要公式、代码和复杂度。

## 1. FACTS-E 2.0 回答框架

| 维度 | 含义 | 必须回答 | 常见失分 |
|---|---|---|---|
| **F — Facts** | 业务事实与问题 | 谁、何时、执行什么任务；AS-IS、Baseline、数据、风险 | 只说“提升效率” |
| **A — Approach** | 方案选择 | 比较规则、搜索、Prompt、RAG、微调、Workflow、Agent | 直接报技术名 |
| **C — Core Technology** | 核心实现 | 数据、模型、检索、工具、权限、日志如何流转 | 只说调用 API |
| **T — Trade-offs** | 技术特点与权衡 | 质量、时延、成本、风险、灵活性、可维护性 | 只讲优点 |
| **S — Success** | 落地效果 | 上线范围、使用情况、业务指标、成本和组织变化 | 把目标当结果 |
| **E — Evaluation** | 评测与迭代 | 评测集、分层指标、错误归因、回归、监控 | 只报“准确率” |

### 1.1 两分钟回答模板

```text
F：谁在什么流程里遇到什么问题？现状指标和风险是什么？
A：比较过哪些更简单或更复杂的方案？为什么选择当前组合？
C：从输入到输出，数据、检索、模型、规则、工具和权限如何流转？
T：核心技术特点是什么？牺牲了什么？边界在哪里？
S：上线到谁、使用多少、业务结果如何？哪些只是设计目标？
E：怎样评测、定位失败、做回归并持续改进？
```

### 1.2 技术题的五步回答法

```text
1. 一句话定义
2. 原理或关键公式
3. 工程价值
4. 局限与取舍
5. 如何验证
```

例如面试官问“为什么使用 Reranker”，不要只答“提高准确率”，而应回答：

> Reranker 对召回候选做更精细的 Query-Document 相关性排序，主要解决排序问题，不补救完全未召回的问题。它通常提升 Top-K 证据质量，但增加模型调用、时延和成本，因此应通过 MRR、NDCG、Context Precision、P95 时延和单请求成本联合验证。

## 4. 高频技术答案卡

### 卡 1｜Transformer 是什么，为什么重要？

**30 秒回答**

Transformer 是以自注意力为核心的序列建模架构。它用 Q、K、V 计算序列位置之间的相关性，用多头注意力捕获不同关系，再通过 FFN、残差连接和归一化完成表示变换。相比顺序执行的 RNN，它更适合并行训练，并能直接建模远距离依赖，因此成为现代语言模型的基础。

**技术深挖**

```text
Attention(Q,K,V) = softmax(QK^T / sqrt(d_k))V
```

编码器通常使用双向注意力；自回归解码器使用 causal mask，只允许关注当前位置之前的 Token。

**业务影响**

- 上下文越长，标准 Attention 的计算和显存成本通常增长很快。
- 选模型时不能只看参数量，还要看上下文、吞吐、首 Token 时延和任务质量。

**追问**

- 为什么除以 `sqrt(d_k)`？
- 为什么要多头？
- Encoder 和 Decoder 的 Mask 有何不同？

### 卡 2｜为什么 Attention 要缩放？

Q、K 的维度增大时，点积方差会增大，Softmax 输入更容易落入饱和区，权重过尖、梯度变小。除以 `sqrt(d_k)` 可以让分数尺度更稳定。

**易错点**

不要只说“防止梯度爆炸”。更准确的表达是：控制点积分布尺度，避免 Softmax 过度饱和，从而改善训练稳定性。

**验证**

观察注意力熵、训练损失、梯度稳定性和收敛速度。

### 卡 3｜为什么使用多头注意力？

每个头在不同投影子空间中学习关系，可以分别关注语法、实体、位置或长距离依赖。每个头通常使用 `d_model / num_heads` 的维度，使拼接后的总维度仍可控。

**权衡**

- 头数过少：表示子空间有限。
- 头数过多：单头维度太小、计算调度复杂，未必提升效果。
- 不能仅凭经验设置，应通过任务评测验证。

### 卡 4｜Padding Mask 和 Causal Mask 的区别

- **Padding Mask**：屏蔽批处理中用于补齐长度的无效位置。
- **Causal Mask**：屏蔽未来 Token，防止自回归训练时信息泄漏。

工程上通常在 Softmax 前把被屏蔽位置加上极小值，使其权重接近 0。

### 卡 5｜位置编码解决什么问题？

自注意力本身对顺序不敏感，位置编码为 Token 注入顺序和距离信息。

| 类型 | 特点 | 主要权衡 |
|---|---|---|
| 正弦绝对位置 | 固定、无需学习 | 灵活性有限 |
| 可学习绝对位置 | 可适配数据 | 外推能力受训练长度影响 |
| 相对位置 | 直接表达相对距离 | 实现更复杂 |
| RoPE | 通过旋转表达相对位置信息 | 长度外推需额外策略 |
| ALiBi | 在注意力分数加入线性距离偏置 | 结构简单，但任务效果需验证 |

### 卡 6｜LayerNorm、BatchNorm、RMSNorm 怎么比较？

- BatchNorm 依赖 Batch 统计量，适合图像等稳定批次场景。
- LayerNorm 在单个样本特征维度上归一化，更适合变长序列和小 Batch。
- RMSNorm 不减均值，只按均方根缩放，计算更简化。

**面试重点**

说明归一化位置也很重要：Pre-Norm 通常更利于深层网络优化；Post-Norm 与原始 Transformer 形式一致，但深层训练稳定性可能更敏感。

### 卡 7｜为什么标准 Self-Attention 是 O(n²)？

长度为 `n` 的序列要计算 `n × n` 的注意力矩阵。超长上下文可采用：

- 局部/滑动窗口注意力；
- 稀疏或块状注意力；
- 线性注意力近似；
- 分层摘要和 RAG；
- FlashAttention 优化 IO，但不等同于把理论复杂度变为 O(n)。

**业务取舍**

“支持更长上下文”不等于“答案一定更好”，还要评估长上下文中的证据发现能力、噪声、时延和成本。

### 卡 8｜BERT 与 GPT 类模型如何选？

- BERT 类 Encoder 模型适合分类、抽取、匹配和表征学习。
- GPT 类 Decoder 模型适合自回归生成、对话和通用任务指令执行。
- 企业系统中常组合使用：小型 Encoder 做 Embedding、分类或 Rerank，生成模型负责回答。

**资料校正提示**

面试时不要把 LLaMA 解释为医学模型，也不要说 GPT 基于 RNN/LSTM。应以 Transformer Encoder/Decoder 架构来描述。

### 卡 9｜Tokenizer、BPE、WordPiece 有什么价值？

子词 Tokenizer 在词表规模和未登录词之间折中。常见词可保持完整，低频词可拆成子词，从而降低 OOV。

**业务影响**

- 中文、代码、型号、错误码和多语言的 Token 效率不同。
- Token 数直接影响上下文容量、时延和费用。
- 领域术语被切得过碎时，可能需要调整词表、数据或选择更合适的模型。

### 卡 10｜什么是过拟合和欠拟合？

- 过拟合：训练集好，未见数据差。
- 欠拟合：训练集本身也学不好。

**处理**

| 问题 | 常见方法 |
|---|---|
| 过拟合 | 更多高质量数据、正则化、Dropout、早停、降低复杂度 |
| 欠拟合 | 增加模型/特征能力、延长训练、改善优化和数据表达 |

**LLM 项目中的映射**

Prompt 在少数测试题上反复调整，也会造成“评测集过拟合”。

### 卡 11｜数据类别不平衡如何处理？

- 分层采样、过采样、欠采样；
- 类别权重、Focal Loss；
- 阈值移动；
- 增加长尾样本和困难负例；
- 使用 Precision、Recall、F1、PR-AUC 等而不是只看 Accuracy。

在 AI 售后项目中，高风险故障虽然少，但漏判成本高，应单独设置召回率和升级率目标。

### 卡 12｜什么时候用 RAG，什么时候微调？

**RAG 更适合**

- 私有、动态、版本化知识；
- 需要引用和追溯；
- 内容频繁变化。

**微调更适合**

- 稳定行为、格式、分类或风格；
- 有足够高质量标注数据；
- Prompt/RAG Baseline 已无法满足。

**组合方式**

RAG 提供事实证据，微调改善行为与格式，规则处理确定性和高风险判断。

### 卡 13｜RAG 的生产链路是什么？

```text
数据接入
→ 解析与治理
→ 分块与索引
→ 查询理解
→ 元数据过滤
→ BM25/向量召回
→ 融合与重排
→ 上下文组装
→ 生成与引用
→ 拒答/工具/人工升级
→ Trace、评测和反馈
```

用户说“模型答错”时，应先判断是知识缺失、解析错误、召回失败、排序错误、生成错误还是业务标准不一致。

### 卡 14｜为什么需要混合检索和 Reranker？

- BM25 擅长错误码、型号、版本、专有名词。
- 向量检索擅长同义改写、口语表达和语义匹配。
- Reranker 对候选做更精细排序。

**验证指标**

Recall@K、MRR、NDCG、Context Precision、P95 时延和单次成本。

### 卡 15｜如何构建企业知识库的元数据？

至少包括：

```text
document_id
source
document_type
language
product_model
region
software/firmware_range
effective_from / effective_to
security_level
review_status
owner
updated_at
```

没有这些字段，系统很难正确处理版本、权限、失效和冲突。

### 卡 16｜如何评测 RAG？

四层评测：

1. **检索层**：Recall@K、MRR、NDCG、过滤正确率。
2. **生成层**：忠实度、正确性、完整性、相关性、引用正确性。
3. **系统层**：任务成功率、拒答、追问、工具成功率、P95 时延、成本。
4. **业务层**：首次解决率、处理时长、升级率、采纳率、单任务成本。

单一 BLEU、ROUGE 或 Accuracy 不能代表生产知识问答质量。

### 卡 17｜SFT、Prompt Tuning、Prefix Tuning、LoRA 的区别

- SFT：使用监督数据调整模型行为，可全参或参数高效微调。
- Prompt Tuning：学习输入侧的软提示参数。
- Prefix Tuning：在多层注意力中学习前缀表示。
- LoRA：冻结主模型，在特定线性层增加低秩增量矩阵。

**选择原则**

先建立 Prompt/RAG Baseline，再根据行为稳定性、数据量、显存和部署方式决定是否微调。

### 卡 18｜为什么 LoRA 能省资源？

LoRA 假设任务适配的权重更新可由较低秩矩阵近似：

```text
ΔW = B × A
```

只训练 A、B，不更新完整 W，因此训练参数、梯度和优化器状态显著减少。

**关键参数**

Rank、Alpha、Dropout、Target Modules、学习率和数据质量。

**验证**

领域任务提升、通用能力退化、不同 Rank 的收益、训练显存和推理成本。

### 卡 19｜什么是灾难性遗忘？

模型在新领域数据上微调后，旧任务或通用能力明显下降。

**原因**

- 新旧数据分布差异；
- 学习率或训练轮数过大；
- 数据窄、重复、标签偏；
- 参数更新覆盖原能力。

**缓解**

混入通用数据、降低学习率、PEFT、回放、正则约束、多任务训练，并对通用集和领域集同时回归。

### 卡 20｜RLHF 的主要流程与不足

经典流程包括 SFT、奖励模型和策略优化。主要不足：

- 人类偏好数据贵且存在偏差；
- 训练链路长、版本迭代慢；
- 策略优化资源消耗高；
- 奖励模型可能被“钻空子”；
- 偏好分数不等于事实正确或业务成功。

面试时应强调：对齐不能替代知识治理、事实验证和业务评测。

### 卡 21｜生成参数如何设置？

| 参数 | 作用 | 风险 |
|---|---|---|
| Temperature | 控制分布平滑程度 | 过高随机，过低僵化 |
| Top-P | 从累计概率集合采样 | 需与 Temperature 联合调节 |
| Top-K | 限制候选 Token 数 | 太小可能损失表达 |
| Max Tokens | 控制输出长度与成本 | 过小截断，过大浪费 |
| Repetition Penalty | 抑制重复 | 过强可能破坏术语和格式 |
| Beam Search | 保留多个候选路径 | 生成慢，开放对话不一定更好 |

企业事实问答通常偏低随机性，并结合结构化输出和规则校验。

### 卡 22｜为什么推理显存一直占用？

显存主要包括：

- 模型参数；
- KV Cache；
- 临时计算缓冲；
- 框架的内存池或缓存分配。

框架保留显存不立即归还，常用于减少重复分配开销，不一定等于内存泄漏。

**排查**

看实际已分配、已保留、KV Cache、并发数、序列长度和 Batch，而不是只看显卡面板总占用。

### 卡 23｜什么是 KV Cache？

自回归生成时，历史 Token 的 Key/Value 可以缓存，避免每生成一个 Token 都重复计算全部历史。

**收益**

降低解码计算。

**代价**

显存随上下文长度、并发、层数和 KV 维度增长。长上下文、高并发服务往往由 KV Cache 而不是参数本身成为瓶颈。

### 卡 24｜FP16、BF16、INT8、INT4 如何选择？

- FP16/BF16：常用于训练和高质量推理。
- INT8：显著降低显存和带宽，通常质量损失较小但依任务而异。
- INT4：压缩更强，质量和硬件适配风险更高。

**不能只比较位宽**

实际速度取决于硬件内核、Batch、序列长度、量化方案和数据分布。量化后必须做领域回归测试。

### 卡 25｜如何做模型服务路由？

```text
规则/缓存
→ 小模型分类或改写
→ 中型模型常规生成
→ 大模型处理复杂任务
→ 高风险转人工
```

路由依据可包括任务类型、难度、风险、SLA、预算和用户等级。

**评测**

端到端成功率、路由正确率、P95 时延、单请求成本和人工升级准确率。

### 卡 26｜Agent 和 Workflow 的区别

- Workflow：路径和分支主要预定义，稳定、可审计。
- Agent：根据中间结果动态决定下一步，更灵活但更难控制。

生产系统优先受控 Agentic Workflow，并设置工具白名单、参数 Schema、最大步数、预算、超时、停止条件和人工确认。

### 卡 27｜如何减少幻觉并保证合规？

1. 权威数据和版本治理；
2. RAG/工具提供事实；
3. Prompt 限定证据边界；
4. 引用校验和结构化输出；
5. 敏感内容、权限和危险操作规则；
6. 不足证据时拒答或升级；
7. 线上监控和人工复核。

“模型诚实”不能只靠一句 Prompt，应由证据、校验、权限和流程共同保证。

### 卡 28｜如何处理隐私和安全？

- 最小权限、租户隔离、文档级 ACL；
- 数据脱敏、日志脱敏、密钥管理；
- Prompt Injection 和越权测试；
- 工具调用审批、幂等和审计；
- 明确数据保留、删除和训练使用边界；
- 对高风险任务设置人工确认。

评测集应包含越权查询、恶意指令、敏感字段和跨租户样本。

### 卡 29｜A/B 测试如何用于大模型？

将用户随机分配到候选方案，比较真实业务表现。除了回答质量，还应观察：

- 任务成功率；
- 用户采纳和满意度；
- 处理时长；
- 人工升级率；
- P95 时延；
- 单任务成本；
- 风险事件。

A/B 前需定义主指标、护栏指标、样本量、实验时长和回滚条件。

### 卡 30｜如何回答“你只是调用 API，技术深度在哪里？”

> 技术深度不在于是否自研基础模型，而在于能否把不确定的模型能力建设成可靠系统。我负责的是业务对象和流程建模、知识版本和权限治理、检索与重排实验、结构化输出和工具安全、四层评测、Trace、灰度发布、成本与时延优化，以及失败闭环。即使更换模型供应商，这些系统能力和业务资产仍然存在。

## 6. 资料中容易误导的口径

以下不是对原资料逐条纠错，而是面试前需要特别警惕的表达：

1. **不要用旧参数规模代表当前模型生态。** 具体模型、版本和能力随时间变化。
2. **LLaMA 不是医学模型。** 它是 Meta 的大语言模型系列。
3. **GPT 的主体不是 RNN/LSTM。** GPT 系列使用 Transformer Decoder。
4. **输入长度不是理论上“无限”。** 模型有训练上下文、位置编码、显存和计算限制。
5. **模型不能可靠地自行知道“自己是否见过这条知识”。** 需要检索、置信机制、拒答和外部验证。
6. **Attention 权重不等同于完整可解释性。**
7. **BLEU/ROUGE/PPL 是特定任务指标，不代表企业问答的业务成功。**
8. **量化不保证一定加速。** 需要硬件和内核支持。
9. **更深、更宽、更多参数不保证业务更好。**
10. **知识注入、行为对齐和实时事实查询应区分。**

## 7. 面试评分 Rubric

| 维度 | 分值 | 高分表现 |
|---|---:|---|
| F 业务事实 | 20 | 有角色、流程、Baseline、数据和风险 |
| A 方案选择 | 15 | 比较多种方案，说明组合架构 |
| C 技术实现 | 20 | 说清数据流、接口、异常、权限和版本 |
| T 技术权衡 | 15 | 有质量/时延/成本/风险取舍 |
| S 落地效果 | 15 | 区分目标、实验和生产结果 |
| E 评测迭代 | 15 | 有评测集、指标、归因、回归和监控 |

### 一票否决式失分

- 编造生产数据；
- 把所有问题归因于模型；
- 无法解释拒答、降级和人工兜底；
- 说不清标准答案和评测分母；
- 高风险任务没有权限和审计；
- 用具体模型名代替方案设计。

## 8. 练习方式

### 第一轮：项目表达

准备三个项目，每个项目形成：

- 2 分钟版本；
- 5 分钟版本；
- 15 分钟深挖版本；
- 一张架构图；
- 一张指标树；
- 一个失败案例。

### 第二轮：30 张答案卡

每张卡完成：

```text
一句话定义
→ 原理/公式
→ 工程价值
→ 局限
→ 评测
→ 两个追问
```

### 第三轮：压力面试

重点练习：

1. 为什么需要 AI？
2. 你只是调用 API 吗？
3. 准确率的分母是什么？
4. 业务没有标准答案怎么办？
5. 成本下降 50% 先优化哪里？
6. P95 必须低于 3 秒牺牲什么？
7. 上线出现错误建议如何止损？
8. 为什么不用更大的模型或更长上下文？
9. 为什么不用自由 Agent？
10. 你的个人贡献是什么？

### 第四轮：按岗位补充

- 产品/解决方案：业务、RAG、评测、ROI。
- 技术产品/架构：Transformer、微调、Agent、部署和 LLMOps。
- 算法工程：公式、代码、复杂度、训练与分布式，见 [算法工程面试补充题库](10-algorithm-engineering-interview-supplement.md)。

## 9. 一段可直接使用的 FACTS-E 示例

> 以下为项目设计示例，不代表已经取得真实生产结果。

**F｜业务问题**  
工业设备售后资料分散在手册、FAQ、工单和研发说明中，同一型号存在固件、地区和语言差异。客服需要反复询问型号、版本和现象，容易引用过期资料，复杂问题升级研发时上下文又不完整。

**A｜方案选择**  
没有选择“上传文档直接聊天”，而是使用结构化数据、规则引擎、RAG、受控 Workflow 和人工升级的组合。实时状态通过 API 查询，确定性错误码和高风险条件由规则处理，文档知识由 RAG 提供，LLM 负责理解、追问和语言生成。

**C｜核心技术**  
文档按类型解析并保留标题、表格、版本和权限元数据；检索采用型号/固件过滤、BM25、向量召回、RRF 和 Reranker；输出使用固定 Schema，包含事实、缺失信息、原因、步骤、证据和升级条件；全链路记录 Trace。

**T｜技术特点**  
核心不是模型更大，而是版本感知、权限隔离、证据可追溯、主动追问和高风险兜底。优先可靠性和可解释性，不让 Agent 自由控制设备；所有参数通过评测选择。

**S｜落地效果**  
灰度阶段分别观察客服采纳率、首次解决率、处理时长、升级率、单工单成本和高风险事件。设计目标与实际结果分开表达。

**E｜评测**  
建立覆盖事实、多条件、多轮、版本冲突、无答案、拒答、多语言和攻击样本的 Golden Dataset。分别评估检索、生成、系统和业务指标；失败按数据、解析、检索、生成、工具和业务定义归因并进入回归集。
