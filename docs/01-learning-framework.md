# 01｜AI 应用技术 × 业务深度能力框架

## 1. 目标不是“会做知识库”，而是能交付业务结果

AI 应用岗位的技术壁垒，不在于知道多少模型和框架名称，而在于能否完成以下闭环：

```text
发现高价值问题
→ 建立业务与数据模型
→ 选择合适的 AI 技术路线
→ 构建可运行系统
→ 建立评测与监控
→ 证明业务价值
→ 持续迭代
```

一个合格的 AI 应用负责人，需要同时理解三个系统：

1. **业务系统**：谁在什么场景下，为了什么目标，执行什么流程。
2. **数据与知识系统**：业务事实如何被记录、更新、授权和检索。
3. **AI 系统**：模型如何得到上下文、如何生成结果、如何被评测和约束。

## 2. 六层能力模型

### 2.1 第一层：业务问题定义

需要掌握：

- 用户、角色、任务、场景、频率和痛点。
- 当前流程、标准流程、异常流程和人工兜底流程。
- 业务对象、状态、字段、规则、权限和组织责任。
- 当前基线：处理时长、错误率、转化率、人工成本、投诉率等。
- AI 介入后希望改变的业务结果。

掌握标准：

- 能把“做一个智能知识库”改写成可验证的问题。
- 能区分用户表达的问题、真正的业务问题和技术问题。
- 能明确哪些环节适合自动化、辅助决策或仅提供信息。

示例：

> 模糊需求：建设售后 AI 知识库。
>
> 可验证需求：针对固件版本、设备状态和错误码明确的常见故障，使一线客服在 3 分钟内给出有出处的排障建议，将技术升级率从 45% 降至 25%，高风险问题必须转人工。

### 2.2 第二层：数据与知识建模

需要掌握：

- 数据源盘点、数据质量、数据血缘与更新机制。
- 结构化、半结构化和非结构化数据的区别。
- 实体、属性、关系、事件和状态。
- 主数据、交易数据、日志数据、知识文档和反馈数据。
- 文档版本、适用范围、有效期、权限和责任人。
- 数据清洗、去重、标注、脱敏和冲突处理。

掌握标准：

- 能设计一套可用于检索、评测和业务分析的数据模型。
- 能识别“文档很多”和“知识可用”之间的差别。
- 能说明每个答案依赖哪些事实、规则和版本。

### 2.3 第三层：AI 与模型基础

需要掌握：

- 机器学习基础：数据集、特征、标签、训练、验证、过拟合和指标。
- LLM 基础：Token、Embedding、Transformer、Attention、上下文窗口和推理。
- 模型选型：质量、成本、时延、上下文、工具调用、结构化输出和隐私。
- Prompt、RAG、微调、工作流、Agent 和规则引擎的边界。

掌握标准：

- 能解释模型为什么可能产生错误。
- 能根据任务特征提出两种以上候选方案。
- 能通过实验选型，而不是根据宣传或个人偏好选型。

### 2.4 第四层：AI 应用工程

需要掌握：

- Python、SQL、Git、HTTP、JSON 和基本 API 开发。
- 文档解析、分块、索引、检索、重排和上下文组装。
- FastAPI、数据库、缓存、队列、Docker 和基础部署。
- 权限、租户隔离、日志、Tracing、超时、重试和降级。
- Prompt 与配置版本管理。

掌握标准：

- 能独立搭建最小可运行系统。
- 能定位一次请求经过了哪些组件以及失败位置。
- 能把 Demo 改造成具备权限、日志和异常处理的服务。

### 2.5 第五层：评测与 LLMOps

需要掌握：

- Golden Dataset、评测维度和评分规则。
- 检索层、生成层、系统层和业务层指标。
- 离线评测、在线实验、人工评审和 LLM-as-a-Judge。
- 错误分类、回归测试、版本对比和生产监控。
- 质量、成本、时延和风险之间的权衡。

掌握标准：

- 不用“感觉回答不错”描述效果。
- 能将“准确率”拆成可测量指标。
- 每次调整模型、Prompt 或检索策略后都能运行固定回归集。

### 2.6 第六层：业务落地与经营结果

需要掌握：

- 试点范围、上线策略、人工审核和责任边界。
- 用户培训、流程改造、反馈闭环和组织协同。
- ROI、TCO、单位任务成本、规模化成本和机会成本。
- 项目风险、合规、安全、数据隐私和供应商依赖。

掌握标准：

- 能给出可执行的上线计划和风险清单。
- 能证明 AI 指标改善如何传导到业务指标。
- 能向业务负责人、技术负责人和管理层分别解释方案。

## 3. T 型能力结构

建议形成“一横一纵”的 T 型能力：

### 横向：AI 应用全链路

业务分析 → 数据治理 → 模型调用 → RAG → 工作流/Agent → 评测 → 部署 → 监控 → ROI。

### 纵向：一个真实行业

选择一个具备真实数据、复杂流程和明确结果指标的行业深入，例如：

- 工业设备售后与运维。
- 制造业质量与供应链。
- 企业软件实施与服务。
- 网络安全风险管理。
- 电梯现场勘测与更新改造。

行业深度至少包括：

- 核心角色。
- 业务对象。
- 状态机。
- 标准流程和异常流程。
- 核心字段。
- 规则与责任边界。
- 业务指标。
- 高频问题与高风险问题。

## 4. 学习闭环：定义—实现—实验—评测—业务化

每学习一个知识点，都必须完成五类产出。

| 阶段 | 问题 | 产出 |
|---|---|---|
| 定义 | 它是什么，与相似概念有何区别？ | 一页概念卡 |
| 实现 | 最小实现需要哪些组件？ | 可运行代码或流程图 |
| 实验 | 哪些参数和方案值得比较？ | 实验矩阵 |
| 评测 | 如何判断哪种方案更好？ | 固定数据集与报告 |
| 业务化 | 改善了什么业务结果？ | ROI 与上线建议 |

禁止以以下行为作为完成标准：

- 只收藏课程。
- 只听懂视频。
- 复制一个框架 Demo。
- 只做聊天 UI。
- 只展示几个成功案例。

## 5. 三档掌握程度

### L1：理解

- 能解释概念。
- 能读懂架构图和示例代码。
- 能说明主要适用场景。

### L2：独立实现

- 能独立搭建最小系统。
- 能修改关键参数。
- 能处理常见异常。

### L3：生产决策

- 能建立评测集和指标。
- 能比较技术路线。
- 能做成本、风险和上线决策。
- 能在真实业务中持续优化。

求职目标至少应达到：

- 机器学习与 LLM 基础：L1～L2。
- RAG、评测、业务建模：L3。
- 工程部署：L2。
- 模型训练与底层系统：根据岗位需要达到 L1～L2。

## 6. 建议的学习时间分配

每周投入 10～12 小时时：

- 课程与文档：30%。
- 编码与实验：35%。
- 评测与错误分析：20%。
- 业务模型和项目文档：15%。

每周必须形成一个可检查产出，例如：

- 一份数据模型。
- 一段可运行代码。
- 一次方案对比实验。
- 一份错误分析报告。
- 一张业务流程或状态机。

## 7. 最重要的判断原则

1. **先定义业务成功，再定义 AI 成功。**
2. **先建立 Baseline，再谈高级方案。**
3. **先建立评测集，再调 Prompt 和模型。**
4. **先判断错误发生在哪一层，再修改系统。**
5. **复杂度必须换来可测量收益。**
6. **能用规则稳定解决的问题，不强行使用大模型。**
7. **高风险场景优先保证可追溯、拒答和人工兜底。**
8. **模型能力不是产品能力，完整系统能力才是。**
