# 03｜生产级 RAG 工程指南

## 1. RAG 不是“把文档放进向量库”

一个生产级 RAG 系统至少包含以下链路：

```text
数据源
→ 解析与清洗
→ 知识建模与版本治理
→ 分块
→ 索引
→ 查询理解
→ 召回
→ 融合与重排
→ 上下文组装
→ 生成
→ 引用、拒答与人工升级
→ 评测、监控和反馈
```

任何一层出现问题，都可能被用户感知为“模型回答错误”。因此排障时必须定位错误层，而不是直接更换模型。

## 2. 第一步：定义 RAG 的任务边界

在开始建设前，先回答：

- 谁使用？客服、客户、技术支持还是内部员工？
- 任务是什么？查事实、排障、生成方案、执行操作还是辅助决策？
- 哪些问题允许回答？
- 哪些问题必须拒答或转人工？
- 答案是否要求引用来源？
- 是否涉及实时数据、个人信息或商业机密？
- 哪些业务指标需要改善？

一个 RAG 系统不应承担所有任务。建议将问题分为：

1. **事实查询**：型号参数、操作步骤、政策和功能说明。
2. **条件判断**：根据版本、状态和环境选择对应规则。
3. **故障诊断**：需要收集信息、排除原因并给出步骤。
4. **执行任务**：查询设备、创建工单、修改配置，需要工具调用。
5. **高风险判断**：安全、法律、财务或重大设备故障，需要人工兜底。

## 3. 数据源与知识治理

### 3.1 数据源分类

| 类型 | 示例 | 主要问题 |
|---|---|---|
| 结构化数据 | 产品表、错误码表、固件版本表 | 字段一致性、主键、实时性 |
| 半结构化数据 | JSON、日志、工单、FAQ | Schema 漂移、噪声、缺失字段 |
| 非结构化数据 | PDF、Word、邮件、聊天记录 | 解析、版本、重复、冲突 |
| 实时数据 | 设备状态、订单、库存 | 工具调用、权限、时延 |
| 反馈数据 | 点赞、客服修改、升级结果 | 偏差、标签质量、闭环 |

### 3.2 文档准入标准

进入知识库前，每份文档至少应具备：

- 唯一 ID。
- 标题和文档类型。
- 来源系统。
- 责任人。
- 生效时间和失效时间。
- 适用产品、型号、地区和语言。
- 固件或软件版本范围。
- 权限等级。
- 审核状态。
- 最近更新时间。

没有这些元数据，系统很难处理版本冲突、权限和过期知识。

### 3.3 数据质量检查

建议检查：

- 空文档和解析失败。
- 重复文档与近似重复段落。
- 扫描 PDF、乱码、错行和表格错位。
- 标题层级丢失。
- 图片中的关键文字未被结构化。
- 同一问题存在多个冲突答案。
- 旧版本未标记失效。
- 文档中包含敏感信息。
- 文档与业务系统数据不一致。

### 3.4 冲突处理优先级

可建立明确规则：

```text
实时业务系统
> 已审核的最新版正式文档
> 已审核 FAQ
> 历史工单经验
> 未审核聊天记录
```

模型不应自行决定哪个冲突来源更可信，优先级应由业务规则和元数据决定。

## 4. 文档解析

### 4.1 解析目标

解析不只是提取纯文本，还应尽量保留：

- 标题层级。
- 段落关系。
- 列表。
- 表格结构。
- 图片说明。
- 页码和章节。
- 链接与附件。
- 版本、型号等结构化字段。

### 4.2 表格处理

表格是企业知识库的高风险点。常见方案：

- 转成 Markdown 表格。
- 将每一行转成自然语言事实。
- 保留列名并为每行生成结构化 JSON。
- 对大表使用 SQL 或工具查询，而不是全部切成文本。

例如错误码表可以转成：

```json
{
  "error_code": "E07",
  "product_model": "X100",
  "firmware_min": "1.4.0",
  "symptom": "刀盘电机异常",
  "possible_causes": ["异物卡住", "电机连接异常"],
  "actions": ["关机检查刀盘", "清除异物", "仍异常则转人工"]
}
```

## 5. 分块策略

### 5.1 固定长度分块

按字符或 Token 长度切分，并设置重叠。

优点：实现简单。

缺点：可能切断语义、步骤和表格结构。

适合：快速 Baseline。

### 5.2 标题层级分块

按章节、标题和段落切分，并保留标题路径。

适合：产品手册、制度和技术文档。

### 5.3 语义分块

根据语义变化位置切分。

优点：内容更完整。

缺点：计算复杂、结果不稳定，需要评测。

### 5.4 父子分块

小块用于检索，大块用于提供上下文。

适合：小问题需要精确命中，但答案依赖更完整章节的场景。

### 5.5 句子窗口

以命中的句子为中心，返回前后若干句。

适合：事实密集但段落较长的文档。

### 5.6 分块实验变量

至少比较：

- Chunk 大小。
- 重叠长度。
- 是否保留标题。
- 是否保留表格结构。
- 是否使用父子关系。
- 不同文档类型是否使用不同策略。

不能只通过肉眼查看几个答案决定分块策略，必须用检索评测集比较 Recall@K、MRR 和噪声比例。

## 6. 索引与检索

### 6.1 关键词检索

适合：

- 错误码。
- 型号。
- 固件版本。
- 专有名称。
- 精确字段值。

### 6.2 向量检索

适合：

- 用户表达与文档措辞不同。
- 同义词和口语化问题。
- 需要语义匹配。

### 6.3 混合检索

工业知识场景通常同时包含精确编号和自然语言描述，建议将 BM25 与向量检索组合。

常见融合方式：

- 加权分数融合。
- Reciprocal Rank Fusion（RRF）。
- 先按元数据过滤，再分别召回。

### 6.4 元数据过滤

检索前应尽可能使用已知条件过滤：

- 产品型号。
- 固件版本。
- 国家和语言。
- 用户权限。
- 文档有效期。
- 产品代际。
- 错误码。

元数据过滤可以减少“检索到内容但适用版本错误”的问题。

### 6.5 多查询与查询拆分

复杂问题可以拆分为多个检索问题。例如：

> “机器 70% 电量为什么回桩，并且回桩后没有继续工作？”

可以拆成：

1. 哪些条件会触发回桩？
2. 哪些条件决定充电后续割？
3. 当前任务状态和日程是否允许续割？

查询扩展会提高召回，但也可能引入噪声，应设置最大查询数并评测成本。

## 7. Query Rewrite

查询改写可以补充对话中的省略信息：

```text
原问题：为什么它又回去了？
上下文：型号 i600，电量 70%，已设置下午 4 点任务，刚开始下雨。
改写后：i600 在电量 70%、存在预约任务且检测到下雨时，哪些条件会触发回充？
```

注意：

- 只能使用已知事实，不能虚构型号和状态。
- 缺失关键条件时应要求用户补充。
- 应保留原始问题用于 Trace 和评测。

## 8. Reranker 重排

推荐链路：

```text
关键词 + 向量召回 Top 30
→ 去重与融合
→ Reranker 重排 Top 10
→ 选择 Top 3～5 进入上下文
```

需要评测：

- 重排是否提升正确文档排名。
- 是否增加明显时延。
- 是否对某些语言或文档类型效果较差。
- Top-N 和 Top-K 的最佳取值。

## 9. 上下文组装

上下文进入模型前应处理：

- 去除重复内容。
- 按可信度、版本和相关性排序。
- 标注文档 ID、标题、版本和来源。
- 控制总 Token。
- 避免把互相冲突的旧版本与新版本混在一起。
- 把结构化事实与自然语言文档分开呈现。

示例：

```text
[来源 1]
文档：i600 用户手册
版本：2026.07
适用固件：>= 01.04.32
章节：雨淋延迟
内容：……

[实时状态]
设备电量：70%
雨淋状态：已触发
当前任务：手动任务
```

## 10. 生成策略

Prompt 至少应包含：

- 只根据提供的证据回答。
- 区分确定事实、可能原因和待确认信息。
- 证据不足时拒答或提问。
- 输出操作步骤时按顺序编号。
- 高风险操作必须提醒停止设备或转人工。
- 给出引用来源。
- 不输出内部敏感字段。

推荐输出结构：

```json
{
  "answer": "...",
  "confidence": "high|medium|low",
  "missing_information": [],
  "possible_causes": [],
  "actions": [],
  "citations": [],
  "escalate": false,
  "escalation_reason": ""
}
```

## 11. 拒答、追问与人工升级

### 11.1 拒答条件

- 未检索到可信证据。
- 检索内容存在无法解决的冲突。
- 用户问题超出产品范围。
- 涉及危险操作。
- 需要实时设备数据但未获得。
- 用户权限不足。

### 11.2 追问条件

故障诊断中缺少关键字段时，应先追问：

- 产品型号。
- 固件版本。
- App 版本。
- 错误码。
- 当前状态。
- 电量。
- 环境条件。
- 问题出现频率。
- 可复现步骤。

### 11.3 人工升级信息包

转人工时应自动整理：

- 用户原始描述。
- 已收集设备信息。
- 已执行步骤。
- 检索到的候选原因。
- 系统不确定点。
- 相关日志和图片。
- 推荐的支持团队。

这样 AI 即使未直接解决问题，也能减少人工重复询问。

## 12. 权限与安全

必须保证：

- 检索前进行权限过滤，而不是生成后再删除。
- 不同客户、租户和部门的数据隔离。
- 敏感字段脱敏。
- Prompt Injection 防护。
- 外部文档不能覆盖系统指令。
- 工具调用使用白名单和参数校验。
- 高风险操作要求二次确认。
- Trace 中的敏感数据按权限保存。

## 13. 版本管理

需要版本化的对象包括：

- 原始文档。
- 解析器。
- 分块策略。
- Embedding 模型。
- 索引。
- 检索参数。
- Reranker。
- Prompt。
- 生成模型。
- 评测集。
- 评分规则。

每次上线记录完整配置，才能复现“为什么这个版本变好了或变差了”。

## 14. RAG 错误归因

| 错误类型 | 表现 | 优先排查 |
|---|---|---|
| 数据缺失 | 没有任何正确依据 | 数据源与知识覆盖 |
| 解析错误 | 表格、标题或文字丢失 | Parser |
| 分块错误 | 正确内容被切散 | Chunking |
| 召回失败 | 正确文档未进 Top-K | Query、Embedding、BM25、过滤 |
| 排名错误 | 正确内容排名过低 | 融合与 Reranker |
| 上下文污染 | 混入旧版本或无关内容 | Metadata、去重、版本规则 |
| 生成错误 | 证据正确但结论错误 | Prompt、模型、结构校验 |
| 拒答错误 | 应答未答或不该答却回答 | 阈值和拒答策略 |
| 业务错误 | 文本正确但无法完成任务 | 流程、工具和业务规则 |

## 15. 建议的实验矩阵

| 实验 | Baseline | 候选方案 | 主要指标 |
|---|---|---|---|
| 分块 | 固定 500 Token | 300/800、标题分块、父子分块 | Recall@K、上下文完整性 |
| 检索 | 向量检索 | BM25、混合检索 | Recall@K、MRR |
| 重排 | 无 | Cross-encoder Reranker | MRR、P95 时延 |
| 查询 | 原问题 | Rewrite、多查询 | 召回、成本 |
| 生成 | 普通 Prompt | 结构化 Prompt、引用、拒答 | Faithfulness、任务成功率 |
| 模型 | 低成本模型 | 高能力模型 | 质量、成本、时延 |

- [ ] 已覆盖拒答、冲突、过期、权限和多语言问题。
- [ ] 已完成检索层和生成层独立评测。
