# 00｜AI 产品经理核心能力总纲

> 更新日期：2026-07-26  
> 定位：作为整个知识库的能力导航页，回答“AI 产品经理最核心要具备什么能力，以及这些能力如何落到项目、评测、产品和经营中”。

---

## 1. 核心结论

AI 产品经理与传统产品经理最大的差异，不只是“更懂模型”，而是需要同时驾驭概率性输出、动态上下文和复杂评测。

最核心的三项能力是：

1. **AI 机会与需求判断**：决定是否值得使用 AI。
2. **AI 产品评测**：决定产品效果是否真的变好。
3. **上下文工程**：决定模型在具体任务中的效果上限。

围绕这三项核心能力，还需要三项构建能力、三项产品化能力和两项经营能力。

```text
三项核心判断力
├─ AI 机会与需求判断
├─ AI 产品评测
└─ 上下文工程

三项构建能力
├─ RAG 与知识策略
├─ Agentic Workflow 与任务编排
└─ 快速原型与实验验证

三项产品化能力
├─ 用户体验与产品设计
├─ 数据分析与持续迭代
└─ 安全、权限与生产治理

两项经营能力
├─ 商业化与单位经济
└─ 交付、续费与规模化
```

# 第一部分｜三项核心能力

## 2. AI 机会与需求判断

### 2.1 定义

AI 机会判断不是判断“模型能不能做”，而是判断：

> AI 相比传统方案是否能够以可接受的成本和风险，创造足够大的增量价值。

### 2.2 五层判断

#### 业务判断

- 用户是否真的存在高频、高成本或高风险问题？
- 当前流程、等待、返工和人工经验依赖是什么？
- 问题的 Baseline 和损失是多少？
- 是否有明确的结果指标？

#### 传统方案判断

优先比较：

```text
流程优化
→ 表单/规则
→ SQL/搜索
→ 传统算法
→ LLM
→ Agent
```

不是所有问题都需要生成式 AI：

- 确定性事实查询优先数据库或 API；
- 规则明确的判断优先规则引擎；
- 错误码和精确术语优先字段查询或 BM25；
- 非结构化理解、总结、生成和跨来源整合更适合 LLM；
- 需要动态规划和多工具执行的任务才可能需要 Agent。

#### AI 可行性判断

- 输入信息是否充分？
- 数据是否存在、可用、可授权和可更新？
- 是否有标准答案或可接受的评价标准？
- 输出是否允许概率性？
- 错误是否能被发现、校验、拒答或转人工？
- 高风险动作是否可设置确认、权限和审计？

#### 价值判断

```text
AI 增量价值
= AI 方案收益
- 传统方案收益
- AI 新增成本
- AI 新增风险
```

新增成本不仅包括 Token 和服务器，还包括：

- 数据治理；
- 评测和标注；
- 系统集成；
- 线上监控；
- 人工审核；
- 错误处理；
- 组织培训；
- 持续维护。

#### 经营判断

- 用户或客户是否愿意持续使用？
- 是否有明确付费意愿？
- 收入能否覆盖模型、交付和维护成本？
- 能否形成标准产品，而不是无限定制？
- 是否具备续费、扩容和跨客户复制的条件？

### 2.3 面试高频问题

1. 为什么这个需求一定要使用 AI？
2. 如果不用大模型，最简单的替代方案是什么？
3. 哪些步骤应该用规则，哪些步骤可以交给 LLM？
4. 一个 AI Demo 效果很好，为什么仍然可能不值得上线？
5. 如何判断一个 Agent 需求是真需求还是技术炫技？
6. 如何评估 AI 项目的综合收益、风险和持续经营价值？

### 2.4 验收标准

能够输出：

- AS-IS 业务流程图；
- Baseline 和问题损失；
- 方案对比矩阵；
- 风险和人工兜底方案；
- AI 增量价值与 ROI 假设；
- Go/No-Go 立项结论。

## 3. AI 产品评测

### 3.1 定义

AI 产品评测的核心，是把主观的“感觉效果不错”转换为：

> **可量化、可比较、可复现、可自动化，并能关联业务结果的评估体系。**

它在 AI 产品中的重要性，接近传统产品中的数据分析能力。

### 3.2 四层评测体系

#### 检索层

判断是否找到正确证据：

- Recall@K；
- Precision@K；
- MRR；
- NDCG；
- 元数据过滤正确率；
- Context Precision。

#### 生成层

判断答案本身是否可靠：

- Correctness；
- Faithfulness；
- Relevance；
- Completeness；
- Citation Correctness；
- 格式与 Schema 正确率。

#### 系统层

判断端到端任务是否完成：

- 任务成功率；
- 正确拒答率；
- 有效追问率；
- 工具调用成功率；
- Agent 轨迹效率；
- 异常恢复率；
- P95 时延；
- 单任务成本。

#### 业务层

判断是否创造真实价值：

- 首次解决率；
- 平均处理时长；
- 用户采纳率；
- 人工升级率；
- 转化率；
- 留存；
- 单任务成本；
- 收入、毛利或风险下降。

### 3.3 评测方法

- 确定性任务：规则、代码或数据库自动评测；
- 半开放任务：Rubric + 人工评分；
- 大规模回归：LLM-as-a-Judge + 人工抽检；
- 工具执行任务：Execution-based Evaluation；
- 真实产品价值：灰度、A/B 测试和业务指标。

### 3.4 关键原则

- 单一 Accuracy 不能代表 AI 产品质量；
- 评测集必须覆盖真实分布、长尾、冲突、无答案和攻击样本；
- 训练集、开发集、测试集和生产回归集必须隔离；
- 失败需要归因为数据、解析、检索、生成、工具、流程或业务定义问题；
- 离线指标上升不等于线上业务结果上升；
- 自动评测不能完全替代领域专家和真实用户行为。

### 3.5 面试高频问题

1. 你说准确率 90%，准确率的定义和分母是什么？
2. RAG Recall@5 很高，为什么回答仍然不好？
3. 如何建设 Golden Dataset？
4. LLM-as-a-Judge 有什么偏差？
5. 如何评估 Agent 的执行过程，而不是只看最终答案？
6. 离线评测变好、线上满意度下降，如何排查？

### 3.6 验收标准

能够输出：

- 一份 Golden Dataset；
- 一套开放式答案 Rubric；
- 检索、生成、系统、业务四层指标树；
- 错误分类体系；
- 回归测试和 Go/No-Go 标准；
- 评测报告和 Bad Case 复盘。

## 4. 上下文工程

### 4.1 定义

上下文工程不是简单的 Prompt Engineering，而是围绕任务动态组织：

```text
系统规则
+ 用户问题
+ 用户身份和权限
+ 历史对话
+ 业务状态
+ 实时系统数据
+ 检索知识
+ 工具返回结果
+ 示例
+ 输出格式
```

其目标是让模型在有限 Token、时延和权限条件下，获得完成任务所需的最优信息。

### 4.2 上下文来源

- System Prompt 和业务规则；
- 用户当前输入；
- 会话历史；
- 用户画像和长期记忆；
- 数据库和实时 API；
- RAG 检索结果；
- 工具调用结果；
- Few-shot 示例；
- 安全规则和输出 Schema。

### 4.3 上下文设计的核心问题

#### 来源

- 信息从哪里来？
- 是否权威、实时、可授权？
- 不同来源冲突时谁优先？

#### 组织

- 顺序如何安排？
- 是否需要标题、标签、XML/JSON 或结构化字段？
- 哪些内容需要去重、聚合和排序？

#### 取舍

- 哪些信息必须保留？
- 哪些内容可以摘要或删除？
- Top-K、Chunk、历史轮数如何决定？

#### 维护

- 多轮对话如何保持业务状态？
- 长期记忆如何更新、更正和删除？
- 知识或权限变化后缓存如何失效？

#### 安全

- 如何防止越权检索？
- 如何隔离租户和用户数据？
- 如何防止 Prompt Injection 污染上下文？

### 4.4 四组关键权衡

1. **长度与成本**：上下文越长，Token、时延和 KV Cache 成本越高。
2. **完整性与噪声**：信息过少会缺证据，过多会稀释关键事实。
3. **个性化与隐私**：长期记忆能改善体验，也会带来越权和错误记忆风险。
4. **灵活性与可控性**：模型动态选择更灵活，程序预定义更可审计。

### 4.5 面试高频问题

1. Prompt 工程与上下文工程有什么区别？
2. 上下文越长是否一定越好？
3. 如何管理多轮对话中的状态和记忆？
4. 如何处理检索到的文档冲突和版本问题？
5. 如何控制上下文 Token、时延和成本？
6. 如何防止用户通过 Prompt Injection 获取无权限信息？

### 4.6 验收标准

能够输出：

- 上下文来源清单；
- Context Assembly 流程图；
- 信息优先级与冲突规则；
- Token 预算；
- 多轮状态与记忆策略；
- 上下文评测和消融实验报告。

# 第二部分｜三项构建能力

## 5. RAG 与知识策略

### 核心能力

- 判断 RAG 的适用和不适用场景；
- 文档解析、元数据、版本和权限治理；
- Query Rewrite、查询拆解和多路召回；
- BM25、向量召回、混合检索和 Reranker；
- 去重、冲突处理、Context Assembly；
- 引用校验、无答案识别和拒答；
- 增量索引、缓存失效和回归测试。

### 不适合使用 RAG 的场景

- 实时、确定性数据：优先 API 或 SQL；
- 规则明确的高风险判断：优先规则引擎；
- 稳定行为、格式和分类：可考虑微调；
- 复杂真实操作：使用受控工具调用和 Workflow。

> “锁影”不是常见的标准 RAG 术语，正式知识库中不采用。相关表达应使用索引、召回、过滤、重排、路由或上下文拼接等明确术语。

---

## 6. Agentic Workflow 与任务编排

### 核心能力

- 任务拆解；
- 状态、分支和停止条件；
- 工具定义和参数 Schema；
- 工具权限、审批、幂等和审计；
- 最大步数、预算、超时和重试；
- 错误恢复和人工接管；
- Agent 轨迹 Trace 和评测；
- 单 Agent、Workflow 和 Multi-Agent 的选型。

### 重要原则

- 不以 Agent 数量作为先进程度；
- 路径确定的任务优先 Workflow；
- 动态规划和多工具选择才需要 Agent；
- Multi-Agent 只在角色、目标、权限或并行任务明显不同且收益可验证时使用；
- 真实执行前必须设置权限、确认和回滚机制。

---

## 7. 快速原型与实验验证

### 核心能力

- 使用模型 API 搭建可交互 Demo；
- 快速替换模型、Prompt、检索和 Workflow；
- 使用脱敏真实样本验证输出；
- 保存输入、输出、Trace、Token、时延和成本；
- 批量运行小型评测集；
- 同时比较两个以上方案；
- 明确 Demo、POC、灰度和生产系统的差异。

### 最小技术要求

- Python 基础；
- HTTP/API 调用；
- JSON 和结构化输出；
- 简单前端或低代码原型；
- 日志读取和错误定位；
- 基础 RAG/Workflow 配置；
- 批量评测脚本。

# 第三部分｜三项产品化能力

## 8. 用户体验与产品设计

- 首次成功体验；
- 能力边界和示例提示；
- 追问、确认和用户控制感；
- 流式输出和等待体验；
- 结果编辑、重试、引用和恢复；
- 人工接管和上下文交接；
- 反馈和纠错闭环；
- AI 不确定性的透明表达。

## 9. 数据分析与持续迭代

- 北极星指标、过程指标和护栏指标；
- 埋点、漏斗、Cohort 和留存；
- 用户和任务分层；
- A/B 测试和灰度；
- 成本、时延和质量联合看板；
- Bad Case 与用户行为关联；
- 数据驱动路线图和资源优先级。

## 10. 安全、权限与生产治理

- 最小权限和租户隔离；
- 数据脱敏、日志脱敏和密钥管理；
- Prompt Injection 和越权测试；
- 工具调用审批、审计和回滚；
- 模型、Prompt、知识和索引版本管理；
- SLA、限流、降级和供应商故障切换；
- 高风险任务的人工确认；
- 线上监控、事故响应和复盘。

## 14. 最终验收

完成本能力总纲后，应能够证明：

1. 能判断一个问题是否真的需要 AI；
2. 能建立可复现的 AI 产品评测体系；
3. 能设计和优化模型所需的上下文；
4. 能选择 RAG、Workflow、Agent、微调或传统方案；
5. 能在一周内搭建可评测的原型；
6. 能将 Demo 升级为有权限、监控、降级和回滚的生产系统；
7. 能用业务指标、成本和 ROI 证明产品价值；
8. 能推动 POC、上线、使用、续费和规模化复制。

> 需求判断决定做不做，评测决定好不好，上下文工程决定效果上限；RAG、Agent 和快速原型负责把判断变成可验证、可交付、可经营的产品。
