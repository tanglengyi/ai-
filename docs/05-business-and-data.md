# 05｜业务深度、数据建模与 AI 方案选型

## 1. AI 项目的起点是业务系统，而不是模型

一个企业真正购买的不是“知识库”“Agent”或“大模型”，而是某种业务结果：

- 减少处理时长。
- 降低人工成本。
- 提高首次解决率。
- 降低错误和风险。
- 提高销售转化。
- 缩短决策周期。
- 扩大服务规模。

因此，AI 项目应从以下问题开始：

```text
谁，在什么场景下，执行什么任务？
当前怎样完成？
最耗时、最容易出错、最依赖经验的环节是什么？
AI 改变哪个环节？
成功如何测量？
失败由谁承担？
```

## 2. 业务分析的六个对象

### 2.1 角色（Actor）

识别所有参与者：

- 最终用户。
- 一线执行人员。
- 领域专家。
- 审核人员。
- 管理者。
- 系统管理员。
- 数据负责人。
- 外部合作伙伴。

不同角色需要不同答案、权限和解释深度。

### 2.2 业务对象（Business Object）

业务中被创建、查询、修改和流转的核心实体，例如：

- 客户。
- 产品。
- 设备。
- 工单。
- 故障。
- 订单。
- 合同。
- 知识文档。
- 风险。

### 2.3 状态（State）

对象在生命周期中的阶段。状态必须有清晰定义、进入条件、退出条件和允许操作。

示例：

```text
工单：新建 → 待诊断 → 处理中 → 待客户确认 → 已解决 → 已关闭
                           ↘ 无法解决 → 升级技术支持
```

### 2.4 事件（Event）

导致状态或数据变化的动作，例如：

- 客户提交问题。
- 设备上报错误码。
- 客服请求诊断。
- 用户确认问题解决。
- 技术支持更新解决方案。

### 2.5 规则（Rule）

确定业务判断的明确条件。规则适合由程序稳定执行，不应全部交给 LLM 自由推断。

例如：

```text
当错误码为 E07 且刀盘堵转次数 >= 3 时：
1. 禁止继续启动刀盘；
2. 提醒用户断电检查；
3. 仍异常时创建高级工单。
```

### 2.6 指标（Metric）

描述流程结果和经营效果。必须先记录当前 Baseline，再判断 AI 是否改善。

## 3. AS-IS 与 TO-BE 流程

### 3.1 AS-IS：当前流程

记录：

- 每一步由谁完成。
- 输入和输出是什么。
- 使用哪些系统。
- 平均耗时和等待时间。
- 高频返工点。
- 决策依赖哪些经验。
- 哪些信息重复录入。
- 哪些异常没有标准处理方式。

### 3.2 TO-BE：目标流程

AI 不只是替换一个搜索框，而应重新分配人和机器的职责：

```text
机器擅长：检索、汇总、分类、抽取、生成草稿、执行确定性工具。
人擅长：目标判断、责任承担、复杂协商、高风险决策、处理例外。
```

目标流程需要明确：

- AI 自动处理的步骤。
- AI 提供建议、由人确认的步骤。
- 必须人工处理的步骤。
- 失败时的降级路径。
- 反馈如何进入知识更新和评测集。

## 4. 数据模型设计

### 4.1 概念模型

首先描述实体及关系。

工业售后示例：

```text
客户 1—N 设备
产品型号 1—N 设备
设备 1—N 固件升级记录
设备 1—N 故障事件
故障事件 1—1 工单
工单 N—N 知识条目
知识条目 N—1 文档版本
```

### 4.2 逻辑模型

定义字段、类型、约束和关系。

设备实体示例：

| 字段 | 类型 | 说明 |
|---|---|---|
| device_id | string | 设备唯一标识 |
| product_model | string | 产品型号 |
| serial_number | string | 序列号，敏感字段 |
| firmware_version | string | 当前固件版本 |
| app_version | string | App 版本 |
| country | string | 使用国家 |
| language | string | 用户语言 |
| current_state | enum | 当前设备状态 |
| battery_level | integer | 电量百分比 |
| last_seen_at | datetime | 最近在线时间 |

### 4.3 主数据与事实数据

- **主数据**：型号、错误码定义、国家、语言、组织、客户等相对稳定对象。
- **事实数据**：一次故障、一次请求、一次工具调用、一次升级和一次处理结果。

RAG 更适合检索知识和说明；实时事实应优先通过数据库或工具查询。

### 4.4 数据血缘

需要知道每个字段和结论来自哪里：

- 原始来源。
- 转换规则。
- 更新频率。
- 责任人。
- 被哪些系统使用。

数据血缘决定答案能否被解释和追责。

## 5. 知识模型

企业知识不只是文档，可以拆成：

1. **事实**：产品参数、版本、状态和实时数据。
2. **规则**：满足什么条件时执行什么动作。
3. **流程**：步骤、角色、输入和输出。
4. **经验**：历史工单中的处理模式。
5. **政策**：服务边界、保修和合规要求。
6. **证据**：日志、图片、检测结果和引用文档。

建议将确定性事实和规则结构化，不要全部压进自然语言文档。

## 6. AI 介入点识别

可从四个维度判断：

### 6.1 任务价值

- 频率是否高？
- 单次耗时是否长？
- 错误成本是否高？
- 是否影响收入、成本或风险？

### 6.2 AI 可行性

- 是否有可用数据？
- 是否有明确的标准答案或评价方式？
- 输入是否能被系统获得？
- 输出是否允许存在概率性？
- 是否能设计人工兜底？

### 6.3 流程可改造性

- 组织是否愿意改变现有工作方式？
- 是否能接入业务系统？
- 是否有负责人维护知识和数据？
- 是否能采集结果反馈？

### 6.4 风险

- 错误建议的后果是什么？
- 是否涉及隐私、商业秘密或安全？
- 是否需要解释和审计？
- 是否存在供应商锁定？

## 7. AI 方案选型

### 7.1 规则引擎

选择条件：

- 规则明确。
- 输入字段完整。
- 输出必须确定。
- 风险高、需要审计。

示例：资格判断、状态流转、阈值报警。

### 7.2 传统搜索

选择条件：

- 用户知道精确关键词。
- 结果以文档列表呈现即可。
- 不需要生成总结。

### 7.3 Prompt + LLM

选择条件：

- 任务依赖输入中已有信息。
- 不需要外部知识。
- 适合摘要、改写、抽取和分类。

### 7.4 RAG

选择条件：

- 需要私有、动态或领域知识。
- 需要引用和可追溯。
- 文档量较大。

### 7.5 微调

选择条件：

- 任务长期稳定。
- 有足够高质量标注数据。
- 需要固定行为、格式、分类能力或风格。
- Baseline 与 Prompt/RAG 已无法满足要求。

### 7.6 Workflow

选择条件：

- 步骤明确。
- 分支有限。
- 需要审计、稳定和可控。

### 7.7 Agent

选择条件：

- 下一步路径无法提前完全定义。
- 需要多次使用工具并根据结果调整计划。
- 错误风险可控。
- 有清晰权限、预算和停止条件。

生产场景应优先考虑受控 Agentic Workflow，而不是无限自由 Agent。

## 8. 复杂业务中的组合架构

真实企业系统通常不是单一技术：

```text
用户问题
→ 意图分类
→ 规则判断是否高风险
→ 查询设备实时状态
→ RAG 检索手册和历史案例
→ LLM 生成诊断建议
→ 规则校验危险操作
→ 用户确认
→ 工具创建工单或执行操作
→ 结果回写业务系统
```

其中：

- 状态和权限由业务系统负责。
- 确定性规则由规则引擎负责。
- 文档知识由 RAG 提供。
- 语言理解和总结由 LLM 负责。
- 真实操作由工具/API 负责。

## 9. AI 业务指标树

### 9.1 技术指标

- 检索召回。
- 忠实度。
- 任务成功率。
- 时延。
- 成本。

### 9.2 使用指标

- 活跃用户。
- 使用频率。
- 采纳率。
- 重试率。
- 转人工率。

### 9.3 流程指标

- 平均处理时长。
- 等待时长。
- 首次解决率。
- 返工率。
- 人工修改率。

### 9.4 经营指标

- 节省工时。
- 单位服务成本。
- 销售转化率。
- 客户留存。
- 投诉和赔付。
- 新增收入。

指标必须建立传导关系。例如：

```text
检索召回提升
→ 有依据答案比例提升
→ 客服采纳率提升
→ 平均处理时长下降
→ 单工单成本下降
```

## 10. ROI 与 TCO

### 10.1 收益估算

```text
年度收益 =
节省人工工时价值
+ 减少错误和返工损失
+ 新增收入或转化收益
+ 风险避免价值
```

### 10.2 成本估算

```text
年度 TCO =
开发成本
+ 数据清洗与标注
+ 模型和基础设施调用
+ 监控与运维
+ 人工审核
+ 知识维护
+ 培训与流程改造
+ 供应商和迁移成本
```

### 10.3 单位经济模型

建议计算：

- 每次请求成本。
- 每个成功任务成本。
- 每个无需人工工单成本。
- 每减少 1 分钟处理时长的成本。

AI 方案只有在规模化后仍具有合理单位经济性，才具备商业价值。

## 11. 客户访谈应该问什么

不要只问“想要什么功能”，应问：

- 最近一次出现这个问题是什么时候？
- 当时谁处理，具体做了哪些步骤？
- 花了多长时间？
- 哪一步最难？
- 需要查询哪些系统和资料？
- 哪些信息经常缺失？
- 如果判断错误会发生什么？
- 最终如何判断问题解决？
- 哪些场景绝对不能由 AI 自动处理？
- 目前每月有多少次、成本多少？

## 12. AI 项目需求文档应增加的内容

传统 PRD 之外，还应包括：

1. 业务目标与 Baseline。
2. AI 任务定义。
3. 数据源和权限。
4. 知识范围和不覆盖范围。
5. 方案选择与对比。
6. 输入、输出和结构化 Schema。
7. 评测集和指标。
8. 拒答、追问和人工升级。
9. 模型、Prompt、索引版本策略。
10. 时延和成本预算。
11. 安全、隐私和合规。
12. 灰度、回滚和运营机制。

## 13. 岗位和项目价值判断

一个 AI 岗位值得深入，通常具备：

- 能接触真实用户和原始问题。
- 能参与数据与知识治理。
- 能负责评测集和质量指标。
- 能参与模型、检索和技术方案选型。
- 能接入真实业务流程和系统。
- 有上线后的业务指标。
- 有真实的错误分析和持续迭代。

若岗位只负责：配置平台、上传文档、设计聊天界面和包装演示，则技术与业务积累有限。

## 14. 核心原则

- 业务复杂度不是低价值，反而是行业壁垒的来源。
- AI 不应抛弃原有 ToB 流程、状态和数据能力，而应把这些能力升级为 AI 系统的结构层。
- 确定性事实交给数据库，确定性规则交给程序，不确定语言任务交给模型。
- 任何 AI 结论都应能追溯到输入、数据、规则或证据。
- AI 项目最终必须回到流程改变和经营结果。
