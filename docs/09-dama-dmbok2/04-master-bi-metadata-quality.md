# 04｜主数据、数据仓库、元数据与数据质量

> 对应原书第 10～13 章，PDF 第 422～609 页。

## 1. 第 10 章：参考数据和主数据

### 1.1 基本定义

| 类型 | 定义 | 示例 |
|---|---|---|
| 主数据 | 描述企业核心业务实体、需要跨流程和系统共享的数据 | 客户、产品、设备、供应商、员工、组织 |
| 参考数据 | 用于分类、约束或解释其他数据的允许值和代码集合 | 国家代码、币种、语言、错误码、状态码 |
| 交易数据 | 记录一次业务活动或事件的数据 | 订单、支付、故障、工单、升级记录 |
| 元数据 | 描述数据定义、结构、来源、规则和使用方式的数据 | 字段定义、表结构、血缘、责任人 |

主数据和参考数据管理的目标不是强行把所有系统改成完全相同，而是对核心对象形成一致识别、权威来源和受控同步。

### 1.2 业务驱动

- 多个部门和系统需要使用相同的客户、产品和组织数据。
- 同一对象在不同系统中有多个编号、名称或定义。
- 数据集成成本过高，接口中存在大量重复映射。
- 分析报表无法确认是否覆盖了全部客户、产品或设备。
- 合并、收购、全球化和多业务线导致系统孤岛。
- 不一致数据造成错误决策、客户体验问题和合规风险。

### 1.3 主数据管理核心活动

```text
确定主数据域和业务价值
→ 识别数据来源和消费者
→ 定义统一业务含义与识别规则
→ 建立匹配、合并和去重规则
→ 确定权威来源和黄金记录
→ 设计发布、同步和变更流程
→ 建立质量、权限和治理机制
→ 持续监控和处理冲突
```

### 1.4 主数据实施模式

| 模式 | 特点 |
|---|---|
| 注册表模式 | 保留各系统数据，通过索引关联同一实体 |
| 整合模式 | 汇总并清洗主数据，主要用于分析消费 |
| 共存模式 | 中心与业务系统共同维护并双向同步 |
| 集中交易模式 | 中心系统成为创建和维护主数据的权威入口 |

模式选择取决于业务控制力、系统改造成本、实时性和组织成熟度。

### 1.5 工业设备示例

- 产品型号、国家、语言、单位、错误码属于参考或主数据。
- 设备序列号对应具体设备实例，不能与产品型号混用。
- 固件版本需要统一格式、版本比较规则和发布日期。
- 错误码定义应包含适用型号、版本、生效时间、风险等级和处理规则。
- 客户在 CRM、售后和电商系统中的记录需要匹配与去重。

## 2. 第 11 章：数据仓库和商务智能

### 2.1 定义

数据仓库将多个来源的历史数据整合到一致模型中，为报表、分析、合规和决策支持提供稳定基础；商务智能通过报表、指标、仪表盘和分析工具帮助用户从数据中获得洞察。

### 2.2 建设目标与原则

1. 聚焦业务目标和优先问题。
2. 以最终分析和决策需求反推数据范围。
3. 全局设计、局部建设、增量交付。
4. 保留明细数据，再按需要汇总。
5. 提升透明度和自助服务能力。
6. 与数据仓库同时建设元数据。
7. 与治理、质量、主数据和集成协同。
8. 根据不同用户提供合适的数据产品。

### 2.3 核心活动

```text
理解业务决策和指标需求
→ 定义数仓与 BI 架构
→ 设计维度、事实和历史模型
→ 获取、转换和加载数据
→ 建设报表、仪表盘和分析产品
→ 验证指标口径与数据质量
→ 发布、运营、配置和版本管理
→ 收集用户反馈并持续优化
```

### 2.4 指标体系设计

每个指标应明确：

- 业务定义。
- 计算公式。
- 统计对象和粒度。
- 时间窗口与时区。
- 数据来源与血缘。
- 更新频率。
- 过滤与排除规则。
- 责任人和审批状态。
- 与其他指标的关系。

“准确率”“解决率”“成本”等词不能只写一个名称，必须定义分母、分子和统计范围。

### 2.5 AI 运营分析示例

| 指标层 | 指标示例 |
|---|---|
| 数据层 | 文档更新时延、元数据完整率、过期内容占比 |
| 检索层 | Recall@K、命中率、无结果率、权限过滤错误率 |
| 生成层 | 忠实度、引用正确率、拒答正确率、格式合规率 |
| 系统层 | 成功率、时延、Token 成本、工具调用失败率 |
| 流程层 | 首次解决率、转人工率、平均处理时长、返工率 |
| 经营层 | 节省工时、单位服务成本、客户满意度、收入影响 |

## 3. 第 12 章：元数据管理

### 3.1 定义

元数据不仅是“关于数据的数据”，还描述业务含义、技术结构、处理规则、数据来源、流转过程、责任人、权限、质量和使用情况。

没有可靠元数据，组织就难以回答：

- 有哪些数据？
- 数据代表什么？
- 数据在哪里？
- 数据从哪里来、经过什么转换？
- 哪些系统和人员在使用？
- 谁负责，谁可以访问？
- 数据是否可信、是否仍然有效？

### 3.2 元数据类型

| 类型 | 示例 |
|---|---|
| 业务元数据 | 术语、指标定义、业务规则、数据所有者、数据域 |
| 技术元数据 | 库表字段、类型、接口结构、模型、索引、作业 |
| 操作元数据 | 运行时间、处理量、失败记录、更新时间、使用频率 |
| 过程元数据 | 转换逻辑、审批流程、质量规则、保留和销毁规则 |
| 社交元数据 | 标签、评分、评论、常见使用方式和专家信息 |

### 3.3 元数据管理活动

```text
定义元数据战略
→ 识别用户和使用场景
→ 设计元数据架构和标准
→ 自动采集技术与操作元数据
→ 人工维护业务定义和责任信息
→ 建立术语、模型、血缘和目录关联
→ 提供搜索、查询、影响分析和报告
→ 监控完整性、新鲜度和使用情况
```

### 3.4 数据血缘

数据血缘描述数据从源头到消费端的路径及转换过程。

一条可用的血缘至少需要包含：

```text
源系统 / 原始文档
→ 原始字段或段落
→ 清洗与转换规则
→ 中间存储或数据管道
→ 目标字段、知识条目或文本块
→ 检索、报表、模型或业务流程
```

血缘用于：

- 回答某个结论为什么出现。
- 分析源数据变更影响哪些下游系统。
- 审计个人数据和敏感数据使用范围。
- 定位错误来自采集、转换、检索还是生成。
- 证明指标、报表和 AI 答案的来源。

### 3.5 RAG 元数据字段建议

| 类别 | 字段示例 |
|---|---|
| 来源 | source_id、source_type、file_hash、source_url |
| 内容 | title、section、page、chunk_id、parent_chunk_id |
| 版本 | version、published_at、effective_from、effective_to |
| 适用范围 | product_model、firmware、country、language、customer |
| 权限 | tenant_id、department、role、security_level |
| 治理 | owner、reviewer、approval_status、retention_policy |
| 质量 | completeness、confidence、last_verified_at |
| 检索 | embedding_model、index_version、keywords、content_type |

向量本身无法表达这些治理要求，必须通过结构化元数据支持过滤、追溯和更新。

## 4. 第 13 章：数据质量

### 4.1 定义

数据质量不是抽象的“数据好不好”，而是数据在具体业务场景中是否适用。相同数据在一个用途下可能合格，在另一个用途下可能不合格。

### 4.2 常见质量维度

| 维度 | 说明 | 示例 |
|---|---|---|
| 准确性 | 是否正确反映真实对象或事件 | 固件版本与设备实际一致 |
| 完整性 | 必需数据是否存在 | 工单必须包含型号和问题描述 |
| 一致性 | 多系统或多字段是否相互一致 | CRM 与售后系统客户国家一致 |
| 及时性 | 是否在需要时更新 | 设备在线状态不是昨天的数据 |
| 唯一性 | 同一实体是否被重复记录 | 一个客户存在多个重复档案 |
| 有效性 | 是否符合格式、范围和规则 | 电量在 0～100 之间 |
| 完整性 / 参照完整性 | 关系是否保持正确 | 工单引用的设备必须存在 |
| 可访问性 | 合法用户能否及时取得 | 客服可在权限内查询手册 |
| 可理解性 | 定义、单位和上下文是否清晰 | “解决率”有明确口径 |

### 4.3 数据质量管理闭环

```text
定义业务用途和质量要求
→ 识别关键数据元素与业务规则
→ 执行数据剖析和基线评估
→ 量化业务影响与风险
→ 确定优先级和改进目标
→ 设计预防、检测和纠正措施
→ 部署质量规则和监控
→ 分析根因、修复流程并复测
→ 持续报告和治理
```

### 4.4 预防优先

| 层级 | 示例 |
|---|---|
| 预防 | 必填校验、枚举、唯一约束、标准接口、清晰定义 |
| 检测 | 剖析、质量规则、异常监控、对账和抽样审核 |
| 纠正 | 去重、标准化、补录、合并、回退和人工复核 |
| 根因治理 | 修改流程、责任、系统设计、培训和激励机制 |

只清洗历史数据而不修改产生错误的流程，会让问题持续复发。

### 4.5 质量规则模板

```text
规则名称：固件版本格式有效性
业务目的：保证版本比较、知识适配和升级判断正确
适用数据：device.firmware_version
规则：必须符合 NN.NN.NN 格式，且版本必须存在于已发布版本清单
严重级别：高
执行频率：实时校验 + 每日批量检查
责任人：设备数据所有者
失败处理：拒绝写入 / 标记异常 / 创建整改任务
质量指标：有效记录数 ÷ 应检查记录数
```

### 4.6 AI 系统质量分层

```text
源数据质量
→ 内容解析与分块质量
→ 元数据质量
→ 索引与检索质量
→ 上下文组合质量
→ 生成与引用质量
→ 业务结果质量
```

模型回答错误不能统一归为“幻觉”。必须判断错误发生在哪一层。

### 4.7 数据质量指标

- 关键数据元素质量达标率。
- 质量规则通过率和趋势。
- 数据问题数量、严重度和平均解决时长。
- 重复问题发生率。
- 低质量数据造成的返工、投诉、损失和风险。
- 质量修复后业务指标改善幅度。
- 数据责任人确认和复核完成率。

## 5. 四章之间的关系

```text
主数据和参考数据
提供统一的核心对象与代码
        ↓
元数据
解释这些数据的含义、来源、责任与血缘
        ↓
数据质量
确保数据满足具体业务用途
        ↓
数据仓库和 BI
基于可信数据形成指标、分析和决策支持
```
