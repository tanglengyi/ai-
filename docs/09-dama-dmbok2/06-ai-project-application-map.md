# 06｜DAMA-DMBOK2 在 AI 应用项目中的落地映射

## 1. 核心结论

一个可上线的 AI 系统不是：

```text
文档 → 切片 → 向量库 → 大模型 → 聊天界面
```

而是：

```text
业务目标与流程
→ 数据治理和责任
→ 业务对象、主数据与参考数据
→ 文档和内容生命周期
→ 数据架构、存储与集成
→ 元数据、血缘、权限和质量
→ RAG / Workflow / Agent / 模型
→ 评测、监控、问题闭环和组织变革
```

DAMA 的作用，是把模型外围那些决定项目成败的数据能力系统化。

## 2. DAMA 知识领域与 AI 项目映射

| DAMA 领域 | AI 项目中的对应问题 | 典型交付物 |
|---|---|---|
| 数据管理 | 数据如何产生、使用、更新、保留和销毁 | 数据生命周期、数据战略和路线图 |
| 数据伦理 | 数据和 AI 输出是否公平、透明、尊重个人 | 伦理风险清单、人工复核和申诉机制 |
| 数据治理 | 谁决策、谁维护、问题如何升级 | 治理章程、RACI、问题管理流程 |
| 数据架构 | 事实、知识、日志和评测数据如何分层 | 目标架构图、数据流图、系统清单 |
| 数据建模 | 业务对象、字段、关系、状态和规则如何表达 | 概念模型、逻辑模型、知识模型 |
| 数据存储和操作 | 数据库、向量库、对象存储如何运行 | 存储分层、备份恢复、变更规范 |
| 数据安全 | 权限、隐私、敏感数据和工具操作如何控制 | 分类分级、权限矩阵、安全控制 |
| 数据集成 | AI 如何查询事实、调用工具和回写系统 | 接口契约、集成架构、错误处理 |
| 文件和内容 | 文档版本、审批、失效和多媒体如何管理 | 内容模型、版本规则、发布流程 |
| 主数据和参考数据 | 客户、产品、型号、错误码是否统一 | 黄金记录、代码表、匹配合并规则 |
| 数仓和 BI | AI 效果和业务价值如何统计 | 指标字典、数据集市、运营看板 |
| 元数据 | 答案来源、适用范围、版本和血缘是什么 | 数据目录、术语表、血缘、索引元数据 |
| 数据质量 | 错误来自源数据、解析、检索还是生成 | 质量规则、错误分类、改进闭环 |
| 大数据和数据科学 | 模型和实验如何开发、部署和监控 | 实验记录、模型卡、漂移监控 |
| 成熟度评估 | 当前是否具备生产化条件 | 成熟度评分、差距和改进路线图 |
| 组织与角色 | 产品、业务、数据、算法和安全如何协作 | 组织模式、岗位职责、RACI |
| 变革管理 | 用户是否真正采用，流程是否真正改变 | 试点、培训、沟通和推广计划 |

## 3. AI 项目的六类数据

### 3.1 业务主数据

相对稳定、跨流程共享的核心实体：

- 客户。
- 产品型号。
- 设备。
- 供应商。
- 组织。
- 员工。
- 国家和语言。

### 3.2 参考数据

用于分类、状态和规则判断的代码：

- 错误码。
- 设备状态。
- 工单状态。
- 风险等级。
- 问题类型。
- 服务政策类型。
- 单位和枚举值。

### 3.3 交易与事件数据

记录实际发生的业务活动：

- 一次设备故障。
- 一次用户提问。
- 一次检索。
- 一次工具调用。
- 一次工单流转。
- 一次模型回答和人工修改。

### 3.4 内容与知识数据

- 产品手册。
- 安装和维护说明。
- FAQ。
- 售后政策。
- 历史工单。
- 培训材料。
- 图片、视频和日志说明。

### 3.5 AI 配置与运行数据

- 模型和 Embedding 版本。
- Prompt 模板。
- 检索与重排参数。
- 工具定义和权限。
- 文本块和向量索引。
- 对话、引用和工具调用日志。

### 3.6 评测与反馈数据

- Golden Dataset。
- 标准答案和证据。
- 错误分类。
- 人工评分。
- 用户采纳、重试和转人工结果。
- 成本、时延、失败率和业务指标。

这六类数据不能全部用同一种存储方式、质量标准和更新机制管理。

## 4. 工业设备售后 AI 项目示例

### 4.1 业务目标

- 降低平均处理时长。
- 提高首次解决率。
- 减少重复咨询和技术升级。
- 让多语言客服获得一致、可追溯的解决方案。
- 防止错误指导造成设备、安全或合规风险。

### 4.2 核心业务对象

```text
客户
设备
产品型号
固件版本
App 版本
错误码
故障事件
工单
知识条目
文档版本
处理步骤
工具动作
评测样本
```

### 4.3 关键权威来源

| 数据 | 权威来源 |
|---|---|
| 设备实时状态 | 设备云平台或设备 API |
| 产品型号和规格 | 产品主数据系统 |
| 固件版本 | 固件发布管理系统 |
| 错误码定义 | 研发维护的参考数据表 |
| 售后政策 | 经审批的政策文档或规则系统 |
| 历史解决方案 | 结构化工单和经审核知识条目 |
| 客户权限和保修 | CRM / 售后业务系统 |

LLM 不能成为这些事实的权威来源。

### 4.4 组合式方案

```text
用户问题
→ 识别语言、意图和设备
→ 查询客户与设备权限
→ 查询实时状态、型号和版本
→ 用规则引擎判断高风险或确定性条件
→ RAG 检索适用文档和历史案例
→ LLM 生成解释和操作步骤
→ 规则校验禁止事项和升级条件
→ 用户确认或人工审核
→ 调用工具创建工单、修改设置或提交日志
→ 回写结果并进入评测与知识改进
```

### 4.5 关键治理规则

1. 只有审批通过且在有效期内的内容可进入生产索引。
2. 检索必须按客户、产品、型号、固件、国家和语言过滤。
3. 高风险操作不得仅由 LLM 决定，必须由规则或人工确认。
4. 设备实时状态必须通过接口查询，不使用历史文档推断。
5. 每个答案必须记录引用、模型、Prompt、索引和工具版本。
6. 发现冲突知识时应停止自动回答并进入问题管理流程。
7. 用户反馈不能直接成为标准知识，必须经过审核。
8. 生产内容失效时，应同步下架索引并保留审计记录。

## 5. AI 质量问题的分层归因

| 层级 | 常见问题 | 处理方向 |
|---|---|---|
| 业务定义 | 问题目标、标准答案或责任边界不清 | 重新定义流程、规则和验收标准 |
| 源数据 | 文档错误、事实过时、字段缺失 | 修复源数据和责任流程 |
| 内容处理 | PDF 解析、表格、图片、分块错误 | 改进解析、结构识别和内容模型 |
| 元数据 | 型号、版本、权限或时间范围缺失 | 补充元数据和自动校验 |
| 检索 | 未召回、错召回、排序错误 | 优化查询、索引、过滤和重排 |
| 上下文 | 证据冲突、过长或拼接顺序错误 | 去重、冲突检测和上下文编排 |
| 生成 | 未遵循证据、格式或拒答规则 | 调整 Prompt、模型、约束和评测 |
| 工具 | 参数错误、权限错误、执行失败 | 完善接口契约、校验、重试和审批 |
| 流程 | 人工接管、回写和反馈闭环缺失 | 重构工作流和责任分工 |
| 运营 | 版本、监控、告警和容量管理不足 | 建立 LLMOps 和数据运维机制 |

## 6. 从 Demo 到生产的四个阶段

### 阶段 1：可行性验证

- 明确一个窄场景和业务指标。
- 使用小规模、已审核数据。
- 建立 30～100 条代表性测试样本。
- 对比搜索、Prompt、RAG、规则和工作流方案。

### 阶段 2：数据与流程治理

- 建立业务对象、术语、元数据和权威来源。
- 设计权限、版本、更新和问题管理流程。
- 定义人工兜底和风险边界。

### 阶段 3：生产化工程

- 接入业务系统和身份权限。
- 建立日志、监控、回滚、备份和成本控制。
- 建立离线回归与上线灰度机制。

### 阶段 4：持续运营

- 分析失败样本和业务结果。
- 更新知识、规则、评测集和流程。
- 定期进行权限复核、成熟度复评和架构优化。
- 用节省工时、质量改善和风险下降证明价值。

## 7. AI 项目数据治理最小闭环

```text
数据准入
→ 结构化与元数据标记
→ 审核和版本发布
→ 权限控制与索引
→ 检索、生成和工具执行
→ 记录证据与结果
→ 质量评测和业务监控
→ 问题归因与责任分配
→ 修复源数据、规则、流程或模型
→ 回归验证并重新发布
```

## 8. 项目验收问题

1. 是否能列出所有关键数据源及其责任人？
2. 是否知道客户、产品、设备和错误码的权威来源？
3. 文档版本冲突和失效时如何处理？
4. 检索是否按业务适用范围和权限过滤？
5. 是否能追溯每个回答使用的证据与版本？
6. 错误能否区分源数据、检索、生成和工具问题？
7. 高风险操作是否有确定性规则和人工兜底？
8. 是否有固定评测集、基线和上线门槛？
9. 上线后由谁维护数据、知识、规则、模型和指标？
10. 项目是否形成了可量化的流程和经营改善？
