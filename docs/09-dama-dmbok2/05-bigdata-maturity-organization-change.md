# 05｜大数据与数据科学、成熟度、组织和变革管理

> 对应原书第 14～17 章，PDF 第 610～758 页。

## 1. 第 14 章：大数据和数据科学

### 1.1 基本认识

大数据不仅指数据量大，还包括数据类型多、产生速度快，以及传统技术难以经济处理的数据。数据科学综合统计、机器学习、计算机科学、建模和可视化方法，从数据中探索模式、形成预测并支持行动。

大数据和数据科学并不脱离数据管理。数据源越多、结构越复杂、模型影响越大，对元数据、质量、安全、伦理和治理的要求越高。

### 1.2 从 BI 到数据科学

| 能力 | 主要回答的问题 |
|---|---|
| 描述性分析 | 发生了什么 |
| 诊断性分析 | 为什么发生 |
| 预测性分析 | 接下来可能发生什么 |
| 规范性分析 | 应采取什么行动 |
| 自动化决策 | 在什么约束下由系统执行行动 |

传统 BI 更多提供历史回顾；数据科学进一步进行探索、预测和干预。但任何预测结果都必须经过业务验证和持续监控。

### 1.3 数据科学生命周期

```text
定义业务问题和价值假设
→ 选择、获取并理解数据源
→ 处理权限、伦理和合规要求
→ 清洗、集成、特征处理和探索
→ 建立基线与候选模型
→ 训练、验证和误差分析
→ 解释结果与业务评审
→ 部署、监控和反馈
→ 根据数据漂移和业务变化迭代
```

### 1.4 模型项目必须管理的对象

- 数据集和样本范围。
- 特征定义和生成逻辑。
- 标签来源与标注质量。
- 训练、验证和测试数据切分。
- 模型、参数和代码版本。
- 实验记录与评测结果。
- 偏差、公平性和伦理风险。
- 部署环境和推理配置。
- 数据漂移、概念漂移和性能衰减。
- 模型退役和替换策略。

### 1.5 数据科学治理

| 治理领域 | 关键问题 |
|---|---|
| 战略 | 模型是否解决优先级足够高的业务问题 |
| 数据 | 数据来源是否合法、完整、代表真实场景 |
| 伦理 | 是否会对个人或群体造成不公平影响 |
| 安全 | 敏感数据、模型和推理接口是否受保护 |
| 质量 | 标签、特征、评测集和结果是否可信 |
| 标准 | 开发、评测、可视化和发布是否遵循统一流程 |
| 可解释 | 能否说明模型依据、限制和失败边界 |
| 监控 | 上线后是否持续检查效果、漂移、成本和风险 |

### 1.6 对生成式 AI 的延伸

生成式 AI 项目同样需要实验可复现：

- 模型供应商和模型版本。
- 系统 Prompt 和模板版本。
- Embedding、重排和索引版本。
- 检索参数、上下文拼接规则。
- 工具定义和权限。
- Golden Dataset 与评分方法。
- 人工评审记录。
- 成本、时延和失败样本。

## 2. 第 15 章：数据管理成熟度评估

### 2.1 成熟度等级

| 等级 | 典型特征 |
|---|---|
| 0 无能力 | 没有识别相关能力，也无明确责任 |
| 1 初始 / 临时 | 依赖个人经验，做法不稳定、不可预测 |
| 2 可重复 | 出现局部流程和规则，但跨团队不一致 |
| 3 已定义 | 形成企业或业务域标准并持续使用 |
| 4 已管理 | 使用指标量化、监控和控制能力 |
| 5 优化 | 基于数据持续改进、自动化并形成反馈闭环 |

成熟度不能靠购买工具直接跨级提升。工具只能支持流程，无法替代责任、标准、治理和行为改变。

### 2.2 成熟度评估目标

- 识别当前优势、弱点和能力差距。
- 为业务与 IT 建立共同语言。
- 根据业务战略确定改进优先级。
- 制定分阶段路线图和投资计划。
- 建立基线并定期复评。
- 对监管、并购、新技术或重大数据问题进行准备度判断。

### 2.3 评估流程

```text
确定评估范围和发起人
→ 选择成熟度模型和评分标准
→ 收集制度、流程、系统、指标和访谈证据
→ 对知识领域和能力进行评分
→ 识别差距、依赖和根因
→ 按业务价值、风险和可行性排序
→ 制定目标状态与改进路线图
→ 批准、执行并跟踪计划
→ 定期重新评估
```

### 2.4 评分证据

成熟度结论不能只来自访谈感受，应综合：

- 正式制度、标准和职责文件。
- 系统配置、数据目录和质量规则。
- 项目与运营流程记录。
- 审计、问题和整改记录。
- 指标趋势和业务结果。
- 员工对制度的实际理解与执行情况。

### 2.5 AI 项目成熟度示例

| 能力 | 1 级表现 | 3 级表现 | 5 级表现 |
|---|---|---|---|
| 知识更新 | 靠个人手工上传 | 有准入、审核、版本和发布流程 | 自动识别变化、回归评测并灰度发布 |
| 评测 | 看几个 Demo | 固定测试集和分层指标 | 线上反馈自动进入错误分析和优化闭环 |
| 安全 | 统一账号访问 | 按组织、角色和文档实施权限 | 持续审计、异常检测和策略自动执行 |
| 可观测性 | 只看接口是否成功 | 记录检索、生成、工具和成本 | 自动归因、告警、容量预测和优化 |
| 治理 | 无明确责任人 | 数据所有者、知识管理员和模型负责人明确 | 决策、指标、风险和价值持续优化 |

## 3. 第 16 章：数据管理组织与角色期望

### 3.1 组织设计前提

没有适用于所有企业的唯一组织结构。设计数据管理组织前，应先了解：

- 数据在战略和核心流程中的作用。
- 企业是集中式、分散式还是矩阵式管理。
- 当前由谁执行数据工作和做数据决策。
- 项目建设与日常运营如何分工。
- 现有委员会、预算和汇报关系。
- 员工的数据知识、协作能力和文化阻力。

应优先识别已经实际承担数据责任的人，再逐步正式化，而不是先创造大量新岗位。

### 3.2 组织模式

| 模式 | 优点 | 风险 |
|---|---|---|
| 分散式 | 靠近业务、响应快 | 定义和标准容易分裂 |
| 网络式 | 通过专家网络协作 | 权责可能不清晰 |
| 集中式 | 统一标准、资源和平台 | 可能距离业务过远、成为瓶颈 |
| 混合式 | 集中能力与本地执行结合 | 边界设计复杂 |
| 联邦式 | 企业定义底线和共享标准，业务域自主执行 | 需要成熟的协商和升级机制 |

### 3.3 关键角色

| 角色 | 职责 |
|---|---|
| 首席数据官 CDO | 数据战略、治理、价值和跨部门协调 |
| 数据治理委员会 | 批准原则、制度、优先级和重大争议 |
| 数据管理办公室 DMO | 运营数据管理项目、标准、指标和能力建设 |
| 数据所有者 | 对数据域定义、质量、权限和使用拥有业务决策权 |
| 数据管理专员 | 维护术语、规则、质量要求并推动问题解决 |
| 数据架构师 | 设计企业数据蓝图和目标架构 |
| 数据建模师 | 建立概念、逻辑和物理模型 |
| 数据工程师 | 建设数据管道、存储、处理和服务能力 |
| 数据质量人员 | 设计规则、评估质量、分析根因和推动整改 |
| 元数据管理员 | 维护目录、术语、血缘和元数据标准 |
| 数据安全与隐私人员 | 分类分级、权限、合规、审计和事件响应 |
| 数据分析师 / 科学家 | 使用数据形成洞察、指标和模型 |
| AI 产品经理 | 将业务问题、数据、模型、流程和指标组织成产品方案 |

### 3.4 RACI 设计原则

每项关键活动应明确：

- **R：Responsible**，实际执行者。
- **A：Accountable**，最终对结果负责且只能有一个。
- **C：Consulted**，需要参与评审和提供意见。
- **I：Informed**，需要被同步结果。

例如“知识条目生效”：业务专家负责内容，数据所有者最终批准，法务和安全参与咨询，客服和开发被同步。

### 3.5 关键成功因素

- 高管支持和稳定资源。
- 明确愿景和与业务战略一致。
- 领导者之间形成共识。
- 利益相关方持续参与。
- 培训、沟通和能力发展。
- 采用度量策略证明价值。
- 坚持原则和责任边界。
- 逐步演进而不是激进重构。

## 4. 第 17 章：数据管理和组织变革管理

### 4.1 数据管理为什么必须管理变革

真正的数据管理改进通常要求：

- 从部门私有数据转向企业共享责任。
- 从事后清洗转向源头预防。
- 从依赖个人经验转向标准流程和可审计决策。
- 从 IT 单方负责转向业务和技术共同负责。
- 从只建设系统转向同时改变角色、考核和工作方式。

这些改变不能只靠上线一个平台完成。

### 4.2 变革法则

1. 组织不会自动改变，真正改变的是人的行为。
2. 人们未必抵制变革，但会抵制被强迫改变。
3. 当前做法通常有历史原因，应先理解再调整。
4. 没有明确推动者，变革会因惯性停止。
5. 技术实现往往比人的协作、信任和利益调整容易。

### 4.3 转型的三个阶段

```text
结束旧状态
→ 中性区 / 过渡期
→ 建立新状态
```

中间阶段最容易出现混乱：旧流程尚未完全停止，新流程还不成熟。需要临时规则、支持渠道、反馈机制和明确的过渡边界。

### 4.4 常见失败原因

- 缺乏紧迫感。
- 指导联盟力量不足。
- 愿景不清晰或没有转化为行为。
- 沟通频率和覆盖面不足。
- 制度、系统、考核或管理者仍在奖励旧行为。
- 没有形成短期可见成果。
- 过早宣布成功。
- 未把新做法嵌入文化、流程和岗位责任。

### 4.5 变革实施路径

```text
建立紧迫感和业务案例
→ 形成跨部门指导联盟
→ 定义目标状态、愿景和路线图
→ 识别利益相关方与阻力
→ 设计沟通、培训和参与机制
→ 清除流程、权限、系统和激励障碍
→ 选择试点并创造短期成果
→ 扩大范围并持续改进
→ 将新行为纳入制度、岗位和绩效
```

### 4.6 沟通设计

不同受众需要不同内容：

| 受众 | 重点信息 |
|---|---|
| 高管 | 业务价值、风险、投资和关键决策 |
| 业务负责人 | 流程变化、责任、收益和资源需求 |
| 一线员工 | 日常工作如何变化、遇到问题找谁 |
| 技术团队 | 标准、接口、控制点、交付物和验收要求 |
| 数据角色 | 决策权、责任边界、问题升级和指标 |
| 客户 / 外部伙伴 | 数据用途、权限、服务变化和支持方式 |

沟通应双向进行，要让利益相关方反馈问题并看到反馈被处理。

### 4.7 AI 项目变革管理

AI 上线后通常改变工作分配，而不是简单减少人数：

```text
AI 自动完成低风险、重复性步骤
→ 员工审核建议和处理例外
→ 专家维护知识、规则和评测样本
→ 管理者根据新指标重新设计流程
```

需要提前处理：

- 员工担心被替代而不愿提供知识。
- AI 建议增加一次审核，反而使流程更慢。
- 绩效仍以处理量衡量，员工没有动力提高知识质量。
- 系统输出错误后责任边界不清。
- 试点效果好，但没有维护预算和长期责任人。

## 5. 四章之间的关系

```text
大数据与数据科学
定义高级数据应用能力
        ↓
成熟度评估
判断组织当前是否具备建设条件
        ↓
组织与角色
确定谁负责、如何协作和如何决策
        ↓
组织变革管理
让新的流程、制度和行为真正持续运行
```
