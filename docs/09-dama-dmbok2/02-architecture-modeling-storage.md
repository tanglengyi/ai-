# 02｜数据架构、数据建模与数据存储操作

> 对应原书第 4～6 章，PDF 第 134～281 页。

## 1. 第 4 章：数据架构

### 1.1 定义

数据架构是与组织战略相协调的数据资产管理蓝图，用来描述当前状态、目标状态、数据需求、数据流、数据标准及数据系统之间的关系。

数据架构的价值不是画一张技术图，而是在业务战略与技术实现之间建立桥梁。

### 1.2 核心成果

| 架构成果 | 说明 |
|---|---|
| 当前状态架构 | 数据存在哪里、由哪些系统产生、如何流动、存在什么问题 |
| 目标状态架构 | 未来需要哪些数据能力、平台和标准 |
| 企业数据模型 | 企业级业务对象、主题域和关系的高层表达 |
| 数据流图 | 数据从来源到消费端的移动、转换和落地路径 |
| 数据平台与存储蓝图 | 数据库、数据仓库、数据湖、对象存储、缓存等定位 |
| 数据集成架构 | API、消息、批处理、实时流、ETL/ELT 的组合方式 |
| 数据标准 | 命名、格式、编码、交换、安全、质量和保留要求 |
| 迁移路线图 | 从现状到目标状态的阶段、依赖、优先级和风险 |

### 1.3 建立企业数据架构的步骤

```text
理解业务战略与能力
→ 识别数据域和关键业务对象
→ 盘点系统、数据存储和接口
→ 描述当前状态与主要问题
→ 定义目标原则和目标状态
→ 开展差距分析
→ 制定项目组合与迁移路线图
→ 通过治理机制持续维护
```

### 1.4 数据架构原则示例

- 业务定义优先于技术字段。
- 关键数据只应有一个权威来源，其他系统通过受控方式复制或引用。
- 数据采集应考虑后续共享、分析和审计需求。
- 接口优先采用标准化、可复用方式，减少点对点连接。
- 数据架构与应用架构、业务架构、技术架构保持一致。
- 架构决策必须记录原因、影响、责任人和适用范围。
- 目标架构应允许分阶段演进，而不是一次性重建全部系统。

### 1.5 AI 项目中的数据架构

一个企业 AI 应用至少需要区分：

```text
业务系统事实数据
├─ 客户、设备、订单、工单、状态、权限
知识与内容数据
├─ 手册、FAQ、政策、历史案例、图片、视频
AI 运行数据
├─ Prompt、模型版本、检索结果、工具调用、回答和反馈
评测与监控数据
└─ 测试集、评分、错误类型、成本、时延和业务结果
```

仅把文档导入向量库不等于完成数据架构。还要明确实时数据、权威来源、权限、版本、血缘和结果回写。

## 2. 第 5 章：数据建模和设计

### 2.1 定义

数据建模是发现、分析和确认数据需求，并用数据模型精确表达和沟通这些需求的过程。

数据模型不仅服务于开发人员，也用于统一业务概念、保存知识、识别规则、分析影响和控制系统复杂度。

### 2.2 三层模型

| 模型层级 | 回答的问题 | 主要内容 |
|---|---|---|
| 概念模型 | 业务中有哪些核心对象，它们有什么关系 | 客户、产品、设备、工单等实体及关系 |
| 逻辑模型 | 每个对象需要哪些字段、规则和约束 | 属性、主键、外键、基数、业务规则、标准定义 |
| 物理模型 | 如何在具体技术中实现 | 表、列、索引、分区、数据类型、文档结构、图节点等 |

### 2.3 常见建模模式

- 关系模型：适合结构稳定、事务一致性要求高的场景。
- 多维模型：适合指标分析、数据仓库和 BI。
- 面向对象模型：与软件对象和复杂行为结合。
- 事实模型：强调事实、角色和约束。
- 时间序列模型：适合设备遥测、金融行情和监控数据。
- NoSQL 模型：包含文档、键值、列族和图模型等，适合特定扩展性和访问模式。

技术选型不应先于访问模式和业务规则。相同业务对象可能同时存在于关系数据库、搜索引擎、图数据库和向量库，但需要明确每种存储承担什么职责。

### 2.4 建模核心活动

```text
规划建模范围和方法
→ 收集业务需求、术语和规则
→ 建立概念模型
→ 建立逻辑模型
→ 设计物理模型
→ 与业务、架构、开发和安全人员评审
→ 发布并纳入元数据管理
→ 随业务和系统变化持续维护
```

### 2.5 模型质量检查

| 检查维度 | 关键问题 |
|---|---|
| 完整性 | 是否覆盖范围内的核心实体、属性、关系和规则 |
| 正确性 | 是否真实反映业务概念与约束 |
| 一致性 | 命名、定义、数据类型和关系是否统一 |
| 清晰性 | 业务和技术人员是否能够理解 |
| 可扩展性 | 新场景加入时是否需要大规模推翻结构 |
| 可追溯性 | 模型元素能否关联需求、来源和系统实现 |
| 可执行性 | 物理设计是否满足性能、安全和运维要求 |

### 2.6 工业售后领域模型示例

```text
客户 1 ─ N 设备
产品型号 1 ─ N 设备
设备 1 ─ N 固件升级记录
设备 1 ─ N 故障事件
故障事件 1 ─ 0..1 工单
工单 N ─ N 知识条目
知识条目 N ─ 1 文档版本
知识条目 N ─ N 适用型号
知识条目 N ─ N 错误码
```

关键设计点：

- “型号”“设备实例”“固件版本”不能混为同一对象。
- 错误码定义属于参考数据，错误事件属于事实数据。
- 知识条目与原始文档版本应分离，保留来源和适用条件。
- 工单状态需要进入条件、退出条件和允许操作。
- 设备实时状态应由业务接口提供，不应由 LLM 猜测。

### 2.7 AI 知识模型

企业知识可拆分为：

| 知识类型 | 推荐表达方式 |
|---|---|
| 事实 | 结构化数据库或 API |
| 规则 | 规则表、决策表、代码或工作流 |
| 流程 | BPMN、状态机或工作流定义 |
| 文档说明 | 文档管理系统与 RAG |
| 术语和定义 | 业务术语表、数据字典、本体 |
| 经验案例 | 结构化案例库与相似检索 |
| 证据 | 日志、图片、检测结果、引用片段 |

不应把所有知识都压缩成自然语言文档后再依赖大模型推理。

## 3. 第 6 章：数据存储和操作

### 3.1 定义

数据存储和操作覆盖数据从创建或获取到归档、保留和处置的全过程，目标是保证数据可用、完整、安全并满足性能要求。

本领域包含两类工作：

1. **数据库技术支持**：选择技术、定义技术架构、安装配置、升级和解决技术问题。
2. **数据库操作支持**：备份恢复、性能监控、容量管理、变更、调度、归档和日常运行。

### 3.2 核心目标

- 管理数据在生命周期中的可用性。
- 保障数据资产完整性。
- 保障事务和查询性能。
- 支撑业务连续性与灾难恢复。
- 降低人工操作错误和不可审计变更。

### 3.3 核心操作能力

| 能力 | 关键实践 |
|---|---|
| 环境管理 | 开发、测试、预发布、生产环境隔离 |
| 配置管理 | 参数、版本、依赖和配置可追踪 |
| 变更管理 | 所有结构和数据变更脚本化、评审、回滚和审计 |
| 备份恢复 | 明确 RPO、RTO，定期执行恢复演练 |
| 性能管理 | 监控吞吐、时延、锁、慢查询、索引和资源使用 |
| 容量管理 | 预测数据增长、存储、计算和网络需求 |
| 高可用 | 冗余、复制、故障切换和健康检查 |
| 数据保留 | 按法律、业务价值和成本确定保留期限 |
| 数据处置 | 安全删除、介质销毁和处置证明 |
| 审计 | 记录访问、变更、导出和高风险操作 |

### 3.4 存储技术选择原则

| 数据与访问特征 | 常见选择 |
|---|---|
| 强事务、关系清晰 | 关系数据库 |
| 大量文档和灵活结构 | 文档数据库 / 对象存储 |
| 高速键值访问 | 键值数据库 / 缓存 |
| 时序事件和遥测 | 时序数据库 |
| 关系网络和路径分析 | 图数据库 |
| 全文检索 | 搜索引擎 |
| 语义相似检索 | 向量数据库或向量索引 |
| 历史分析 | 数据仓库 / 湖仓 |

向量数据库不是企业知识的唯一存储。它通常只保存向量、文本片段和检索元数据，权威事实、权限和业务状态仍需由其他系统承担。

### 3.5 AI 系统存储分层示例

```text
关系数据库
├─ 用户、组织、权限、设备、工单、任务状态
对象存储
├─ 原始文档、图片、音频、日志包
搜索 / 向量索引
├─ 分块内容、关键词、向量、过滤字段
缓存
├─ 会话状态、短期结果、热点数据
数据仓库
├─ 使用、质量、成本、评测和业务指标
审计存储
└─ Prompt、检索证据、模型输出、工具调用和审批记录
```

### 3.6 运维指标

- 可用性和故障时长。
- 备份成功率与恢复演练通过率。
- RPO、RTO 达成率。
- 查询和写入时延。
- 容量使用率与增长趋势。
- 变更失败率与回滚次数。
- 未授权访问和高风险操作数量。
- 数据保留与删除任务完成率。
