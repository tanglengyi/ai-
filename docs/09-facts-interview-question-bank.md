# 09｜FACTS-E：AI 大模型项目面试题库

> 适用岗位：AI Solutions Product Manager、AI Technical Product Manager、AI Solution Architect、AI Application Architect、行业 AI 解决方案经理。  
> 资料来源：`大模型面试题.pdf`、`LLMs大模型面试问题和答案97页.pdf` 中的 LLM 基础、Transformer、RAG、文档解析、微调、PEFT、Agent、推理部署、评测、显存与分布式训练等主题。  
> 整理原则：不按“概念背诵题”堆砌，而是按 **业务问题 → 方案选择 → 技术实现 → 技术权衡 → 落地结果 → 评测迭代** 重组。

## 1. FACTS-E 回答框架

本题库使用 `FACTS-E` 作为项目面试回答骨架：

| 维度 | 含义 | 面试官真正想判断什么 |
|---|---|---|
| **F — Facts** | 业务事实与问题 | 你是否理解用户、流程、数据、基线和风险，而不是只会讲模型 |
| **A — Approach** | 解决方案与选型 | 你是否比较过规则、搜索、Prompt、RAG、微调、Workflow、Agent |
| **C — Core Technology** | 核心技术实现 | 你是否理解数据链路、检索链路、生成链路、工具调用和工程架构 |
| **T — Trade-offs** | 技术特点与权衡 | 你是否知道方案的优缺点、边界，以及质量、成本、时延和风险的取舍 |
| **S — Success** | 落地效果 | 你是否真正上线、推动使用，并改变了效率、成本、质量或风险 |
| **E — Evaluation** | 评测与持续迭代 | 你能否把“不确定的模型能力”变成可测量、可定位、可回归的系统 |

### 1.1 两分钟项目回答模板

```text
F：在什么业务场景中，谁遇到了什么问题？原流程、基线和风险是什么？
A：比较过哪些方案，为什么选择当前组合方案？
C：系统由哪些核心模块组成，数据如何流转？
T：方案的技术特点、关键参数、边界和取舍是什么？
S：上线范围、用户规模、效果、成本和组织变化是什么？
E：如何构建评测集、定义指标、做错误归因和持续回归？
```

### 1.2 面试回答的合格标准

一个完整项目回答至少应出现以下内容：

- 明确用户、任务、业务流程和 Baseline。
- 解释为什么需要 AI，以及为什么不使用更简单的方案。
- 能画出端到端数据与系统链路。
- 能区分数据、检索、生成、工具和业务规则问题。
- 不把“准确率”当成唯一指标。
- 能说明失败、降级、拒答、人工升级和版本治理。
- 效果数据必须区分：实际结果、试验结果、设计目标。

## 2. 通用项目深挖题：按 FACTS-E 六个维度

## 2.1 F｜业务事实与问题

1. 这个项目最初由谁提出，为什么要做？
   - 回答重点：业务触发事件、责任部门、真实损失或机会，不要只说“公司要拥抱 AI”。

2. 目标用户是谁？最终使用者、决策者、付费者是否为同一角色？
   - 回答重点：角色、权限、使用频率、决策链和价值差异。

3. 用户在什么时间、地点和流程节点使用系统？
   - 回答重点：具体任务，而不是笼统描述“提升效率”。

4. AS-IS 流程是什么？每一步由谁完成，输入、输出和耗时分别是什么？

5. 原流程最耗时、最容易出错、最依赖经验的环节是什么？

6. 问题的业务 Baseline 是什么？
   - 可用指标：平均处理时长、首次解决率、升级率、返工率、转化率、单任务成本。

7. 问题是高频低风险，还是低频高风险？为什么值得优先解决？

8. 现有搜索、FAQ、规则系统或人工流程为什么不能解决？

9. 任务是否存在统一标准答案？如果部门口径不一致，如何处理？

10. 数据是否真实存在、可获取、可授权、可持续更新？

11. 业务对象有哪些？它们之间是什么关系？
    - 示例：客户、设备、型号、固件、错误码、工单、知识条目、解决结果。

12. 哪些字段是完成任务必需的？缺失时会发生什么？

13. 哪些事实来自文档，哪些来自实时业务系统，哪些来自人工经验？

14. 业务中有哪些确定性规则，不应该交给 LLM 自由推断？

15. 错误答案的后果是什么？谁承担责任？

16. 哪些问题允许直接回答，哪些必须拒答或转人工？

17. 项目第一阶段明确不做什么？为什么？

18. 用户是否愿意改变现有工作方式？系统如何嵌入原流程？

19. 知识、规则和评测数据分别由谁维护？

20. 如果不做这个项目，业务会继续承受什么成本或风险？

## 2.2 A｜解决方案与选型

1. 你比较过哪些方案？为什么最终不是单纯的搜索或 FAQ？

2. 如何判断使用 Prompt、Workflow、RAG、微调还是 Agent？

3. 为什么选择 RAG，而不是把全部领域知识微调进模型？

4. 哪些部分使用规则引擎，哪些部分使用 LLM？

5. 为什么使用 Workflow，而不是自由 Agent？

6. 如果使用 Agent，它的工具权限、预算、最大步数和停止条件是什么？

7. 结构化数据库、全文检索、向量数据库和知识图谱分别承担什么任务？

8. 如何处理用户信息不足的问题：猜测、追问、拒答还是转人工？

9. 如何处理同一问题存在多个版本、地区或型号答案？

10. 如何处理实时数据与静态文档不一致？

11. 如何设计高风险问题的人工兜底链路？

12. 系统失败时有哪些降级方案？
    - 示例：大模型不可用时返回搜索结果；向量检索不可用时使用 BM25；工具失败时生成工单。

13. 为什么选择自建、采购 SaaS、调用模型 API 或私有化部署？

14. 如何选择基础模型？比较了哪些质量、成本、时延、上下文和合规指标？

15. 多语言方案是先翻译再检索，还是多语言 Embedding 直接检索？为什么？

16. 如何设计答案结构，避免模型直接输出不可控的长文本？

17. 为什么需要引用来源？引用是给用户看，还是给审核与追责使用？

18. 如何将一次 Demo 拆成 MVP、灰度上线和生产化三个阶段？

19. 哪些功能是“看起来智能但业务价值低”的伪需求？

20. 如果只能保留一个 AI 能力，你会保留哪个，为什么？

## 2.3 C｜核心技术实现

1. 请画出系统端到端架构和一次请求的完整链路。

2. 数据源有哪些？如何接入、解析、清洗、去重和脱敏？

3. PDF、Word、网页、表格、图片和历史工单分别如何解析？

4. 为什么文档解析不能只提取纯文本？需要保留哪些结构信息？

5. 如何设计文档元数据？
   - 至少包含：文档 ID、版本、适用型号、地区、语言、生效时间、失效时间、权限、审核状态和责任人。

6. 文档如何分块？固定长度、标题分块、语义分块、父子分块如何选择？

7. Chunk Size 和 Overlap 如何做实验，而不是凭感觉设置？

8. 表格如何进入知识库？什么时候不应把大表切成文本？

9. 为什么工业知识通常需要 BM25 与向量检索结合？

10. 混合检索如何融合？加权分数和 RRF 有什么差异？

11. Embedding 模型如何选择？如何验证中文、多语言、专业术语和长文本能力？

12. 什么是 Recall@K、Precision@K、MRR 和 NDCG？分别解决什么问题？

13. 为什么需要 Reranker？它解决召回还是排序问题？

14. 元数据过滤是在召回前还是召回后做？各有什么影响？

15. Query Rewrite 如何补全多轮对话中的省略信息？如何避免虚构条件？

16. 复杂问题如何拆成多个子查询？查询扩展为什么可能同时提升召回和噪声？

17. Top-K 如何选择？上下文越多是否一定越好？

18. 上下文组装时如何处理重复、冲突、顺序和 Token 预算？

19. Prompt 中如何约束模型只基于证据回答？

20. 如何实现引用校验，防止“有引用但引用不支持答案”？

21. 如何实现正确拒答，而不是让模型随意说“我不知道”？

22. 如何输出稳定 JSON，并校验 Schema、必填字段和枚举值？

23. 工具调用如何设计参数校验、权限校验、幂等、重试和超时？

24. 多轮对话的短期记忆、长期记忆和业务状态分别放在哪里？

25. 如何防御 Prompt Injection、越权检索和敏感数据泄露？

26. 如何记录 Trace，定位一次错误经过了哪些节点、模型、Prompt、索引和工具？

27. 模型、Prompt、Embedding、索引和知识库版本如何关联？

28. 如何做缓存？语义缓存可能带来什么版本和权限风险？

29. 如何支持知识更新后的增量索引与回滚？

30. 线上系统如何监控请求量、时延、错误、成本、拒答和人工升级？

## 2.4 T｜技术特点、边界与权衡

1. 你的方案最核心的技术特点是什么？不要只回答“用了 LangChain”。

2. RAG 的优势和局限分别是什么？

3. 微调的优势和局限分别是什么？

4. Workflow 与 Agent 在可控性、灵活性、成本和风险上的差异是什么？

5. 为什么模型越大不一定越适合业务？

6. 如何在准确率、时延、成本和风险之间做取舍？

7. 提高 Top-K 为什么可能降低最终答案质量？

8. 更大的 Chunk 为什么可能提高完整性，却降低精确召回？

9. Reranker 能提升什么，又会增加什么成本？

10. 使用长上下文直接塞全文，与 RAG 相比有什么优缺点？

11. 规则和 LLM 组合为什么比“全交给大模型”更可靠？

12. 结构化事实与非结构化知识为什么应分开处理？

13. 多语言检索中，翻译误差、术语一致性和跨语言 Embedding 如何权衡？

14. 如何减少幻觉？为什么 RAG 也不能彻底消除幻觉？

15. 如何避免模型把“可能原因”表述为“确定结论”？

16. Temperature、Top-P、Top-K、重复惩罚分别影响什么？

17. 量化会怎样影响显存、速度和质量？INT8、INT4 应如何验证？

18. 模型蒸馏、量化、剪枝和小模型路由分别适合什么场景？

19. 私有化部署和云 API 在数据安全、弹性、维护和成本上的权衡是什么？

20. 如何降低供应商锁定风险？

21. 如何判断技术复杂度已经超过业务收益？

22. 哪些问题属于模型能力边界，哪些属于企业数据和业务定义问题？

23. 为什么“回答看起来更流畅”不等于“系统效果更好”？

24. 为什么离线指标提升，线上业务指标可能没有提升？

25. 项目中最重要的一次技术取舍是什么？你放弃了什么？

## 2.5 S｜落地效果

1. 系统是否真实上线？上线到哪些用户、地区、产品或业务流程？

2. 上线前 Baseline 和上线后结果分别是什么？统计周期多长？

3. 结果是实验数据、灰度数据还是全量生产数据？

4. 使用率、活跃率和客服采纳率如何？用户为什么愿意或不愿意用？

5. 平均处理时长、首次解决率、人工升级率和单工单成本变化了多少？

6. 质量提升是来自模型，还是来自数据治理、流程改造和规则统一？

7. 有没有出现“指标提升但用户体验下降”的情况？

8. 系统最常见的失败类型是什么？发生频率如何？

9. 上线后出现过什么严重问题？如何止损、回滚和复盘？

10. 项目减少了哪些人工工作，又新增了哪些知识维护和审核工作？

11. 业务团队的职责和流程发生了什么变化？

12. 系统是否真正减少了研发或技术支持的重复工作？

13. 成本如何计算：模型调用、向量库、服务器、评测、标注和运维分别多少？

14. ROI 如何计算？收益是节省成本、增加收入还是降低风险？

15. 项目能否复制到其他产品、地区或部门？复制的前提是什么？

16. 哪些指标没有达到目标？为什么？

17. 如果重新做一次，你会优先改变哪三件事？

18. 你的个人贡献是什么？哪些成果是你直接推动的？

## 2.6 E｜评测与持续迭代

1. 客户问“准确率多少”时，你会先追问什么？

2. 如何区分检索正确率、答案正确性、忠实度、任务成功率和业务效果？

3. Golden Dataset 从哪里来？谁负责审核？

4. 评测集如何覆盖真实业务分布，而不是只覆盖简单 FAQ？

5. 如何覆盖同义改写、多条件、多轮、版本冲突、无答案、拒答、转人工、多语言和攻击样本？

6. 训练集、开发集、验证集、测试集和生产回归集如何划分？

7. 如何避免在测试集上反复调参造成评测泄漏？

8. 检索层使用哪些指标？为什么 Recall@K 高并不代表答案一定好？

9. 生成层如何评估 Faithfulness、Correctness、Relevance、Completeness 和 Citation Correctness？

10. 系统层如何评估任务成功率、正确拒答率、追问有效率、工具成功率和时延？

11. 业务层如何评估首次解决率、处理时长、升级率、满意度和单任务成本？

12. 开放式答案如何设计 Rubric？

13. 哪些指标适合确定性规则评测，哪些适合人工或 LLM-as-a-Judge？

14. LLM-as-a-Judge 有哪些偏差？如何与人工评分对齐？

15. 如何定义上线阈值和 Go/No-Go 标准？

16. 如何做错误分类？
    - 数据问题、解析问题、检索问题、生成问题、工具问题、流程问题、业务定义问题。

17. 为什么每次实验最好只修改一个主要变量？

18. 一次实验需要记录哪些版本和参数？

19. 如何比较不同模型、Chunk、Embedding、Top-K 和 Reranker？

20. 如何评估成本和时延，而不是只看质量？

21. 如何做灰度发布、A/B 测试和回滚？

22. 线上如何发现知识过期、用户问题漂移和模型退化？

23. 如何把失败样本转成知识更新、Prompt 更新和回归测试样本？

24. 人工修改答案如何进入闭环，又如何避免把错误经验写回知识库？

25. 如何向客户解释“系统不能保证 100% 正确”，同时给出可信的上线方案？

## 6. 面试回答评分 Rubric

每道项目题可按 100 分评分：

| 维度 | 分值 | 高分表现 |
|---|---:|---|
| 业务事实 F | 20 | 有角色、场景、AS-IS、Baseline、数据和风险 |
| 方案选择 A | 15 | 比较过多个方案，能解释为什么选择组合架构 |
| 技术实现 C | 20 | 能画链路、说清模块、数据流、接口和异常处理 |
| 技术权衡 T | 15 | 能说优缺点、边界、参数和质量/成本/时延取舍 |
| 落地效果 S | 15 | 区分目标与实际结果，有上线范围、使用和 ROI |
| 评测迭代 E | 15 | 有评测集、分层指标、错误归因、回归与监控 |

### 常见扣分项

- 只讲框架名和模型名，不讲业务问题。
- 只说“准确率提高”，没有定义指标和分母。
- 把设计目标说成已经实现的结果。
- 所有问题都归因于模型，不分析数据和业务规则。
- 只会讲理想流程，没有失败、降级和人工兜底。
- 无法解释为什么选择 RAG、微调或 Agent。
- 不能说明自己具体做了什么。

## 8. 一段可用于面试的 FACTS-E 示例

> 以下为项目设计示例，不代表已经取得的真实生产结果。

**F｜业务问题**  
工业设备售后资料分散在手册、FAQ、工单和研发说明中，同一型号又存在固件、地区和语言差异。客服需要反复询问型号、版本和现象，容易引用过期资料，复杂问题还要升级研发，导致处理时间长、口径不一致、升级信息不完整。

**A｜解决方案**  
没有选择“上传文档直接聊天”，而是采用规则引擎、结构化数据、RAG、Workflow 和人工升级的组合架构。实时设备状态通过 API 查询，确定性错误码和高风险条件由规则处理，文档知识通过 RAG 检索，LLM 负责问题理解、追问和语言生成。

**C｜核心技术**  
文档按类型解析并保留标题、表格、版本和权限元数据；检索使用型号/固件过滤、BM25、向量召回、RRF 和 Reranker；生成结果采用固定 JSON Schema，包含已知事实、缺失信息、可能原因、操作步骤、证据和升级条件；全链路记录 Trace。

**T｜技术特点**  
特点不是单纯“模型更强”，而是版本感知、权限隔离、证据可追溯、主动追问和高风险兜底。取舍上优先可靠性和可解释性，不让 Agent 自由执行设备操作；检索和模型参数通过评测集选择，而不是追求最大模型或最长上下文。

**S｜落地效果**  
上线时应分别观察客服采纳率、首次解决率、平均处理时长、人工升级率、单工单成本和高风险事件。设计目标只能作为目标，必须用灰度试验和生产数据验证后再对外表达。

**E｜评测**  
建立覆盖事实题、多条件题、多轮追问、版本冲突、无答案、拒答、多语言和攻击样本的 Golden Dataset。分别评估检索 Recall@K、答案忠实度与完整性、任务成功率与 P95 时延，以及首次解决率和人工升级率；失败样本按数据、解析、检索、生成、工具和业务定义进行归因并进入回归集。
