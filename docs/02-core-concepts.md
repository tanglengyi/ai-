# 02｜AI、LLM、RAG、Agent 与评测核心定义

本章的目标不是背术语，而是建立一套能用于方案设计、问题定位和技术沟通的共同语言。

## 1. AI、机器学习与生成式 AI

### 1.1 人工智能（Artificial Intelligence，AI）

使计算机完成通常需要人类认知能力的任务的技术集合，包括感知、预测、决策、规划、生成和交互。

AI 是上位概念，规则系统、机器学习、深度学习和大模型应用都可以属于 AI。

### 1.2 机器学习（Machine Learning，ML）

让系统从数据中学习模式，并对未见数据进行预测或决策的方法。典型流程包括：准备数据、训练模型、验证模型、部署推理和持续监控。

### 1.3 深度学习（Deep Learning，DL）

以多层神经网络为核心的机器学习方法。它能够从大量数据中自动学习复杂表示，常用于图像、语音和自然语言任务。

### 1.4 生成式 AI（Generative AI）

根据输入生成新内容的 AI，包括文本、图像、音频、视频、代码和结构化数据。生成结果具有概率性，因此必须通过约束、检索、评测和人工兜底管理不确定性。

### 1.5 基础模型（Foundation Model）

在大规模通用数据上训练、可以适配多种下游任务的模型。大语言模型是基础模型的一类。

### 1.6 大语言模型（Large Language Model，LLM）

使用大规模文本或多模态数据训练，能够根据上下文预测并生成 Token 序列的模型。它擅长语言理解、生成、摘要、分类、抽取、推理和工具调用，但并不天然等于事实数据库或业务规则引擎。

## 2. 模型运行基础

### 2.1 Token

模型处理文本时的基本单位。一个 Token 可能是一个汉字、一个英文单词的一部分、标点或特殊符号。

Token 数量直接影响：

- 上下文是否放得下。
- 推理时延。
- API 成本。
- 输出长度。

### 2.2 Tokenizer

将原始文本转换成 Token ID，并将模型输出的 Token ID 还原为文本的组件。不同模型的分词方式可能不同，因此相同文本在不同模型中的 Token 数也可能不同。

### 2.3 Embedding

将文本、图像或其他对象表示为高维数值向量。语义相近的内容通常在向量空间中距离更近。

Embedding 常用于：

- 语义检索。
- 聚类与去重。
- 相似问题匹配。
- 推荐和分类。

Embedding 本身不是答案，它只是对象的数值表示。

### 2.4 Transformer

现代大语言模型的核心网络架构。它通过 Attention 机制并行处理序列中的关系，能够建模长距离依赖。

### 2.5 Attention

模型在处理某个 Token 时，对上下文中其他 Token 分配不同权重的机制。它帮助模型判断哪些信息对当前生成最重要。

Attention 不意味着模型真正理解事实，也不能保证模型只关注正确内容。

### 2.6 参数（Parameter）

模型通过训练学习到的数值。参数规模会影响模型容量，但模型质量还受到数据、架构、训练方法、推理策略和任务适配等因素影响，不能仅凭参数量判断效果。

### 2.7 上下文窗口（Context Window）

一次请求中模型能够处理的最大 Token 范围，通常包含系统提示、历史对话、检索内容、工具结果和用户输入。

上下文越长不一定越好。无关内容过多会增加成本、时延和注意力干扰。

### 2.8 推理（Inference）

模型训练完成后，根据新输入生成预测或答案的过程。生产系统关注的不只是模型能否回答，还包括推理时延、并发、吞吐、稳定性和成本。

### 2.9 Temperature

控制生成随机性的采样参数。通常：

- 较低：结果更稳定，适合抽取、分类和业务问答。
- 较高：结果更多样，适合创意生成。

Temperature 不是准确率开关。降低 Temperature 不能消除知识缺失或错误检索。

### 2.10 Top-p

核采样参数。模型只在累计概率达到指定阈值的候选 Token 集合中采样。通常不需要同时大幅调整 Temperature 和 Top-p，应通过固定评测集验证效果。

### 2.11 幻觉（Hallucination）

模型生成看似合理但缺乏依据、与事实冲突或无法由给定上下文支持的内容。

常见原因：

- 问题超出模型或知识库覆盖范围。
- 检索内容错误或缺失。
- 上下文存在冲突。
- Prompt 鼓励模型必须回答。
- 任务需要精确计算、实时事实或外部工具。
- 模型在概率生成过程中补全了不存在的信息。

## 3. Prompt 与结构化输出

### 3.1 Prompt

提供给模型的指令和上下文，包括角色、目标、约束、输入、示例、输出格式和拒答规则。

高质量 Prompt 应明确：

- 任务是什么。
- 可使用哪些证据。
- 什么情况下拒答。
- 输出必须包含什么。
- 禁止做什么。

### 3.2 System Prompt

系统级指令，定义模型的长期行为、角色、工具权限、边界和输出要求。它通常比普通用户输入具有更高优先级。

### 3.3 Few-shot Prompting

在 Prompt 中提供少量输入—输出示例，帮助模型理解任务格式和判断标准。示例必须覆盖关键边界，错误示例会直接引导错误行为。

### 3.4 Structured Output

要求模型按照 JSON Schema 或其他明确结构输出结果。适用于字段抽取、接口调用、工作流节点和后续程序处理。

结构正确不等于内容正确，仍需进行业务校验。

## 4. RAG 与检索系统

### 4.1 RAG（Retrieval-Augmented Generation）

检索增强生成。系统先从外部数据源检索相关信息，再把检索结果作为上下文交给模型生成答案。

RAG 主要解决：

- 私有知识。
- 频繁更新的知识。
- 需要引用依据的问答。
- 超出模型训练知识范围的领域内容。

RAG 不能自动解决：

- 原始数据质量差。
- 业务规则相互冲突。
- 文档权限缺失。
- 问题需要执行真实操作但系统没有工具。
- 评测目标不明确。

### 4.2 Document Parsing

将 PDF、Word、网页、表格等原始文件解析为可处理文本、结构和元数据的过程。解析质量直接决定后续检索上限。

### 4.3 Chunk

将长文档切分得到的文本单元。Chunk 过小可能丢失上下文，过大可能引入噪声并增加 Token 成本。

### 4.4 Chunking

文档分块策略，包括固定长度、按段落、按标题层级、语义分块、父子分块和句子窗口等。

### 4.5 Metadata

描述文档或 Chunk 的结构化信息，例如：产品型号、固件版本、语言、地区、文档类型、生效时间、权限和来源。

Metadata 可用于过滤、排序、权限控制、引用和错误分析。

### 4.6 Index

为提升检索速度而建立的数据结构。RAG 中常见索引包括倒排索引和向量索引。

### 4.7 Vector Database

存储向量并支持近似最近邻搜索的数据库或检索系统。它通常还支持元数据过滤，但并不负责保证业务知识正确。

### 4.8 Semantic Search

通过 Embedding 相似度检索语义相关内容。它能找到措辞不同但含义相近的文本，但对精确编号、专有名词和错误码可能不如关键词检索稳定。

### 4.9 BM25

经典关键词相关性排序算法，基于词频、逆文档频率和文档长度等因素评分。适合错误码、型号、名称和精确术语检索。

### 4.10 Hybrid Search

组合关键词检索与向量检索，再融合两类结果。它通常比单一检索方式更适合工业、法律、售后和企业知识场景。

### 4.11 Reranker

对初步召回的一组候选文档进行更精细的相关性重排。常见流程是先快速召回 Top-N，再由重排模型选出 Top-K。

### 4.12 Query Rewrite

根据上下文对用户问题进行改写、补全或拆分，以提高检索效果。例如把“为什么它回去了”改写成包含设备型号、剩余电量和任务状态的完整查询。

### 4.13 Parent-Child Retrieval

使用较小 Chunk 做精确检索，但返回其所属的较大父级内容给模型，以兼顾召回精度和上下文完整性。

### 4.14 Context Assembly

对检索结果去重、排序、截断、标注来源并组合成最终上下文的过程。它决定哪些证据真正进入模型。

## 5. 微调与模型适配

### 5.1 Fine-tuning

使用特定数据继续训练预训练模型，使其更适应某种任务、风格、格式或行为。

微调通常适合：

- 稳定的分类或抽取任务。
- 固定输出风格和格式。
- 特定行为模式。
- Prompt 很长且重复的任务。

不适合仅为了让模型记住频繁变化的知识。

### 5.2 SFT（Supervised Fine-Tuning）

使用人工或程序构造的标准输入—输出样本进行监督微调，使模型学习期望行为。

### 5.3 PEFT（Parameter-Efficient Fine-Tuning）

只训练模型少量新增或选定参数的高效微调方法，用于降低显存和计算成本。

### 5.4 LoRA

一种常见 PEFT 方法，通过低秩矩阵近似参数更新，不直接完整更新所有模型参数。

### 5.5 RLHF

基于人类反馈的强化学习。通常通过偏好数据、奖励模型和强化学习，使模型输出更符合人类偏好和安全要求。

### 5.6 RAG 与微调的核心区别

- RAG 主要改变模型在回答时获得的外部知识。
- 微调主要改变模型的行为、任务能力或输出模式。
- 动态知识、引用和私有数据优先考虑 RAG。
- 稳定任务、格式、风格和行为优先考虑微调。
- 两者可以组合，但必须通过评测证明组合收益。

## 6. Workflow、Agent 与工具调用

### 6.1 Workflow

由预先定义的步骤、分支和规则组成的流程。执行路径大多可预测，适合稳定、可审计的业务过程。

### 6.2 Agent

由模型根据目标、上下文和当前状态动态决定下一步行动的系统。它可能调用工具、读取结果、继续规划并最终完成任务。

Agent 的自由度更高，同时也带来更高的不确定性、成本和安全风险。

### 6.3 Tool Calling / Function Calling

模型按照预定义接口生成工具名称和参数，由程序执行真实操作，再把结果返回给模型。

工具调用适合：

- 查询实时数据。
- 读取数据库。
- 执行计算。
- 创建工单。
- 调用业务系统。

### 6.4 Agentic Workflow

在部分步骤中允许模型动态决策、但整体仍受流程和边界控制的系统。生产环境通常比完全开放式 Agent 更容易治理。

### 6.5 Memory

为跨轮次或跨任务保留信息的机制。可以分为：

- 短期记忆：当前上下文中的对话状态。
- 长期记忆：持久化的用户偏好、事实或历史记录。
- 工作记忆：执行任务过程中临时保存的中间结果。

记忆必须考虑准确性、更新、遗忘、权限和隐私。

## 7. 评测核心定义

### 7.1 Golden Dataset

经过人工审核、代表真实业务分布、包含预期结果和评分标准的固定评测集。它用于版本对比和回归测试。

### 7.2 Baseline

用于比较的基础方案。例如：人工流程、关键词搜索、基础 Prompt 或无重排的 RAG。

没有 Baseline，就无法判断复杂方案是否真正改善效果。

### 7.3 Accuracy

预测正确样本数占总样本数的比例。它适合类别相对均衡、答案可明确判定的任务，但不能直接代表开放式问答质量。

### 7.4 Precision

被系统判定为正例的样本中，真正为正例的比例。

### 7.5 Recall

所有真实正例中，被系统成功识别出的比例。

### 7.6 F1 Score

Precision 与 Recall 的调和平均，用于平衡两者。

### 7.7 Recall@K

前 K 个检索结果中包含相关内容的查询比例。它用于衡量检索系统是否把正确证据召回。

### 7.8 MRR（Mean Reciprocal Rank）

根据第一个正确结果出现的排名计算平均倒数排名。正确结果越靠前，MRR 越高。

### 7.9 Context Precision

检索上下文中真正相关内容所占的程度。它关注返回结果是否包含过多噪声。

### 7.10 Faithfulness

生成答案中的陈述是否能由给定检索上下文支持。它用于衡量答案是否忠于证据。

### 7.11 Answer Relevance

生成答案是否直接、完整地回应用户问题。

### 7.12 Groundedness

回答是否建立在提供的事实、数据或工具结果之上，而不是自由发挥。不同评测框架对它和 Faithfulness 的具体定义可能略有不同，使用时必须写清评分标准。

### 7.13 LLM-as-a-Judge

使用大模型按照评分规则评价另一个模型的输出。它适合规模化评测，但可能存在位置偏差、措辞偏差和模型偏好，必须用人工样本校准。

### 7.14 Human Evaluation

由领域专家或目标用户按照明确 Rubric 进行评价。成本较高，但对于高风险、复杂和主观任务不可替代。

### 7.15 Task Success Rate

用户任务最终成功完成的比例。它比单纯文本相似度更接近真实产品效果。

### 7.16 Containment Rate

问题无需人工介入、由自动系统完整解决的比例。不能为了追求高自动解决率而错误阻止人工升级。

### 7.17 Escalation Rate

需要升级到人工或更高级支持的比例。应同时关注“正确升级”和“错误升级”。

## 8. 生产工程与 LLMOps

### 8.1 LLMOps

围绕 LLM 应用的数据、Prompt、模型、评测、部署、监控和迭代管理方法。

### 8.2 Observability

使系统内部运行状态可被观察和分析的能力。包括请求链路、Prompt、检索结果、工具调用、Token、时延、错误和最终输出。

### 8.3 Trace

一次完整请求经过各组件的执行记录。Trace 是定位 RAG 和 Agent 错误的重要依据。

### 8.4 Latency

从请求开始到响应完成所需时间。常关注 P50、P95、P99，而不只看平均值。

### 8.5 Throughput

单位时间内系统能够处理的请求量。

### 8.6 Guardrail

用于约束输入、输出或执行行为的机制，包括敏感信息检测、内容安全、结构校验、事实校验、权限校验和工具白名单。

### 8.7 Fallback

主方案失败时采用的降级策略，例如换模型、改用关键词搜索、返回引用、要求补充信息或转人工。

### 8.8 Regression Test

系统更新后重新运行固定评测集，确保原有能力没有退化。

### 8.9 TCO（Total Cost of Ownership）

系统全生命周期总成本，包括模型调用、向量数据库、开发、运维、评测、人工审核、数据治理和供应商迁移成本。

## 9. 方案选择速查

| 问题特征 | 优先方案 |
|---|---|
| 规则明确、结果确定、风险高 | 规则引擎 / Workflow |
| 需要私有或实时知识、要求引用 | RAG |
| 固定分类、抽取、风格或格式 | Fine-tuning / 结构化 Prompt |
| 需要查询实时系统或执行操作 | Tool Calling |
| 步骤稳定、审计要求高 | Workflow |
| 路径无法预先穷举、需动态决策 | 受控 Agent |
| 文档知识变化 + 行为需要稳定 | RAG + Fine-tuning |
| 简单任务即可解决 | 不增加不必要的 Agent 或复杂 RAG |
