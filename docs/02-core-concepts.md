# 02｜AI、LLM、RAG、Agent 与评测核心定义

> 本章的目标不是背诵术语，而是建立一套可以用于方案设计、问题定位、技术沟通和项目评审的共同语言。

## 阅读方法

| 学习动作 | 需要回答的问题 | 掌握标准 |
|---|---|---|
| 理解定义 | 这个概念是什么？ | 能用自己的语言准确解释 |
| 理解边界 | 它能解决什么，不能解决什么？ | 不把模型能力、检索能力和业务规则混为一谈 |
| 理解场景 | 什么情况下应该使用？ | 能结合实际业务案例判断 |
| 理解风险 | 使用时最容易出现什么问题？ | 能提出约束、评测或兜底方案 |
| 理解关系 | 它与相近概念有什么区别？ | 能完成技术选型与方案对比 |

## 1. AI、机器学习与生成式 AI

| 编号 | 概念 | 英文 / 缩写 | 定义 | 典型能力或场景 | 关键边界 |
|---|---|---|---|---|---|
| 1.1 | 人工智能 | Artificial Intelligence，AI | 使计算机完成通常需要人类认知能力任务的技术集合。 | 感知、预测、决策、规划、生成、交互。 | AI 是上位概念，规则系统、机器学习、深度学习和大模型应用都可以属于 AI。 |
| 1.2 | 机器学习 | Machine Learning，ML | 让系统从数据中学习模式，并对未见数据进行预测或决策的方法。 | 数据准备、模型训练、验证、部署推理、持续监控。 | 依赖数据分布和训练目标；训练集表现好不代表真实环境表现好。 |
| 1.3 | 深度学习 | Deep Learning，DL | 以多层神经网络为核心的机器学习方法，能够从大量数据中学习复杂表示。 | 图像识别、语音识别、自然语言处理、多模态任务。 | 通常需要较多数据和计算资源，且结果解释难度较高。 |
| 1.4 | 生成式 AI | Generative AI | 根据输入生成新内容的 AI。 | 文本、图像、音频、视频、代码、结构化数据生成。 | 生成结果具有概率性，必须通过约束、检索、评测和人工兜底管理不确定性。 |
| 1.5 | 基础模型 | Foundation Model | 在大规模通用数据上训练、可适配多种下游任务的模型。 | 通过 Prompt、RAG、微调等方式适配不同业务。 | 基础模型不等于可直接上线的业务系统。 |
| 1.6 | 大语言模型 | Large Language Model，LLM | 使用大规模文本或多模态数据训练，根据上下文预测并生成 Token 序列的模型。 | 理解、生成、摘要、分类、抽取、推理、代码生成、工具调用。 | LLM 不天然等于事实数据库、搜索引擎或业务规则引擎。 |

## 2. 模型运行基础

| 编号 | 概念 | 英文 / 缩写 | 定义 | 主要影响或用途 | 注意事项 |
|---|---|---|---|---|---|
| 2.1 | Token | Token | 模型处理文本时的基本单位，可能是一个汉字、英文单词的一部分、标点或特殊符号。 | 上下文容量、推理时延、API 成本、输出长度。 | Token 不等于字数；不同模型的 Token 计算方式不同。 |
| 2.2 | 分词器 | Tokenizer | 将原始文本转换为 Token ID，并将模型输出的 Token ID 还原为文本的组件。 | 决定文本如何被模型切分和编码。 | 相同文本在不同模型中的 Token 数可能不同。 |
| 2.3 | 向量表示 | Embedding | 将文本、图像或其他对象表示为高维数值向量，语义相近的内容通常距离更近。 | 语义检索、聚类、去重、相似问题匹配、推荐、分类。 | Embedding 只是对象的数值表示，本身不是答案，也不保证业务正确性。 |
| 2.4 | Transformer | Transformer | 现代大语言模型常用的核心网络架构，通过 Attention 并行处理序列关系。 | 建模上下文关系和长距离依赖。 | Transformer 是架构，不等于某一个具体模型或产品。 |
| 2.5 | 注意力机制 | Attention | 模型处理某个 Token 时，为上下文中的其他 Token 分配不同权重的机制。 | 判断哪些上下文信息更影响当前生成。 | Attention 不代表模型真正理解事实，也不能保证关注的信息一定正确。 |
| 2.6 | 参数 | Parameter | 模型通过训练学习得到的数值。 | 决定模型表达和拟合能力的一部分。 | 参数规模不是质量的唯一标准，还受数据、架构、训练方法和任务适配影响。 |
| 2.7 | 上下文窗口 | Context Window | 一次请求中模型能够处理的最大 Token 范围。 | 容纳系统提示、历史对话、检索内容、工具结果和用户输入。 | 上下文越长不一定越好；无关内容会增加成本、时延和注意力干扰。 |
| 2.8 | 推理 | Inference | 模型训练完成后，根据新输入生成预测或答案的过程。 | 在线问答、生成、分类、抽取、工具决策。 | 生产环境还要关注时延、并发、吞吐、稳定性和成本。 |
| 2.9 | 温度 | Temperature | 控制生成随机性的采样参数。 | 较低时更稳定，适合抽取、分类和业务问答；较高时更多样，适合创意生成。 | Temperature 不是准确率开关，降低它不能解决知识缺失或错误检索。 |
| 2.10 | 核采样 | Top-p | 模型只在累计概率达到指定阈值的候选 Token 集合中采样。 | 调整输出的多样性和集中程度。 | 通常不需要同时大幅调整 Temperature 和 Top-p，应通过固定评测集验证。 |
| 2.11 | 幻觉 | Hallucination | 模型生成看似合理，但缺乏依据、与事实冲突或无法由给定上下文支持的内容。 | 常见于知识缺失、检索失败、上下文冲突、实时事实和精确计算任务。 | 应通过引用、拒答、工具调用、规则校验、评测和人工升级治理。 |

### 幻觉常见原因

| 原因类别 | 具体表现 | 对应改进方向 |
|---|---|---|
| 知识覆盖不足 | 问题超出模型或知识库范围 | 补充知识源、允许拒答、转人工 |
| 检索错误 | 没有召回正确资料，或召回了错误版本 | 优化分块、Metadata、混合检索、重排 |
| 上下文冲突 | 多份文档结论不一致 | 增加版本、生效时间和优先级规则 |
| Prompt 约束错误 | 指令要求模型必须给出答案 | 明确证据范围和拒答条件 |
| 缺少外部工具 | 任务需要实时数据、精确计算或系统操作 | 使用 Tool Calling 或规则引擎 |
| 概率生成特性 | 模型补全了不存在的信息 | 结构校验、事实校验、固定评测与人工审核 |

## 3. Prompt 与结构化输出

| 编号 | 概念 | 英文 / 缩写 | 定义 | 适用场景 | 关键注意事项 |
|---|---|---|---|---|---|
| 3.1 | 提示词 | Prompt | 提供给模型的指令和上下文，可包含角色、目标、约束、输入、示例、输出格式和拒答规则。 | 问答、抽取、分类、总结、生成和工具决策。 | 应明确任务、证据范围、拒答条件、必填内容和禁止事项。 |
| 3.2 | 系统提示词 | System Prompt | 定义模型长期行为、角色、工具权限、边界和输出要求的系统级指令。 | 统一产品行为、权限控制、角色设定、输出规范。 | 通常优先级高于普通用户输入，但仍不能代替业务校验和权限控制。 |
| 3.3 | 少样本提示 | Few-shot Prompting | 在 Prompt 中提供少量输入—输出示例，帮助模型理解格式和判断标准。 | 分类、抽取、格式化输出、复杂边界判断。 | 示例应覆盖关键边界；错误或片面的示例会直接引导错误行为。 |
| 3.4 | 结构化输出 | Structured Output | 要求模型按照 JSON Schema 或其他明确结构输出结果。 | 字段抽取、接口调用、工作流节点、后续程序处理。 | 结构正确不等于内容正确，仍需类型、枚举、规则和业务一致性校验。 |

## 4. RAG 与检索系统

| 编号 | 概念 | 英文 / 缩写 | 定义 | 主要用途 | 关键边界或风险 |
|---|---|---|---|---|---|
| 4.1 | 检索增强生成 | Retrieval-Augmented Generation，RAG | 系统先从外部数据源检索相关信息，再把检索结果作为上下文交给模型生成答案。 | 私有知识、动态知识、需要引用依据的问答、领域知识补充。 | 不能自动解决数据质量差、规则冲突、权限缺失、缺少工具和评测目标不明确等问题。 |
| 4.2 | 文档解析 | Document Parsing | 将 PDF、Word、网页、表格等原始文件解析为可处理的文本、结构和元数据。 | 为分块、索引、检索和引用提供基础数据。 | 解析质量直接决定后续检索上限；表格、图片、页眉页脚最容易出错。 |
| 4.3 | 文本块 | Chunk | 长文档切分后形成的文本单元。 | 作为检索、重排和上下文拼装的基本单位。 | 过小会丢失上下文，过大会引入噪声并增加 Token 成本。 |
| 4.4 | 分块策略 | Chunking | 将文档切分为 Chunk 的方法。 | 固定长度、按段落、按标题、语义分块、父子分块、句子窗口。 | 应结合文档结构、问题类型和评测结果选择，不能只靠固定字数。 |
| 4.5 | 元数据 | Metadata | 描述文档或 Chunk 的结构化信息。 | 型号、固件版本、语言、地区、文档类型、生效时间、权限、来源过滤。 | Metadata 设计不足会导致版本错误、权限泄漏和引用不可追溯。 |
| 4.6 | 索引 | Index | 为提升检索速度建立的数据结构。 | 倒排索引、向量索引及其他搜索索引。 | 索引只提升检索能力，不保证原始知识正确。 |
| 4.7 | 向量数据库 | Vector Database | 存储向量并支持近似最近邻搜索的数据库或检索系统。 | 向量检索、相似度搜索、Metadata 过滤。 | 向量数据库不是完整知识库，也不负责业务正确性和文档治理。 |
| 4.8 | 语义检索 | Semantic Search | 通过 Embedding 相似度检索语义相关内容。 | 找到措辞不同但含义相近的问题和文档。 | 对精确编号、专有名词、型号和错误码可能不如关键词检索稳定。 |
| 4.9 | 关键词排序算法 | BM25 | 基于词频、逆文档频率和文档长度等因素进行相关性排序的经典算法。 | 错误码、型号、名称、专有词和精确术语检索。 | 对语义相似但用词差异较大的内容召回能力有限。 |
| 4.10 | 混合检索 | Hybrid Search | 组合关键词检索与向量检索，并融合两类结果。 | 工业、法律、售后和企业知识场景。 | 融合权重和排序方式必须通过评测确定。 |
| 4.11 | 重排模型 | Reranker | 对初步召回的候选文档进行更精细的相关性重排。 | 先召回 Top-N，再选出更相关的 Top-K。 | 会增加时延和成本，应验证是否真正提升最终答案。 |
| 4.12 | 查询改写 | Query Rewrite | 根据上下文对用户问题进行补全、改写或拆分。 | 将模糊问题转换为更适合检索的查询。 | 改写不能擅自加入用户未提供的事实；必要时应先追问。 |
| 4.13 | 父子检索 | Parent-Child Retrieval | 使用较小 Chunk 精确检索，但返回其所属的较大父级内容给模型。 | 同时兼顾召回精度和上下文完整性。 | 父级内容过大仍可能引入噪声，需要控制返回范围。 |
| 4.14 | 上下文组装 | Context Assembly | 对检索结果去重、排序、截断、标注来源并组合成最终上下文。 | 决定哪些证据真正进入模型。 | 需要控制重复、冲突、Token 预算、来源优先级和版本有效性。 |

### RAG 能解决与不能自动解决的问题

| 类别 | 具体问题 | 是否适合仅靠 RAG | 建议方案 |
|---|---|---|---|
| 私有知识问答 | 模型训练数据中没有企业内部文档 | 是 | RAG + 权限控制 + 引用 |
| 高频更新知识 | 产品版本、政策、价格经常变化 | 是 | RAG + 版本管理 + 生效时间 |
| 需要证据引用 | 回答必须指出依据 | 是 | RAG + 引用校验 |
| 原始数据质量差 | 文档错误、缺失、重复、冲突 | 否 | 先进行数据治理和知识审核 |
| 业务规则复杂 | 多条件决策、审批、状态流转 | 否 | 规则引擎 / Workflow + RAG |
| 需要执行操作 | 创建工单、查询订单、修改状态 | 否 | Tool Calling / API / Workflow |
| 权限要求严格 | 不同角色只能访问部分资料 | 否 | 身份认证 + 行级或文档级权限过滤 |
| 成功标准不明确 | 不知道什么答案算正确 | 否 | 先建设 Golden Dataset 和评测体系 |

## 5. 微调与模型适配

| 编号 | 概念 | 英文 / 缩写 | 定义 | 适用场景 | 关键边界或风险 |
|---|---|---|---|---|---|
| 5.1 | 微调 | Fine-tuning | 使用特定数据继续训练预训练模型，使其更适应某种任务、风格、格式或行为。 | 稳定分类、抽取、固定风格、固定格式、特定行为、重复且很长的 Prompt。 | 不适合仅为了让模型记住频繁变化的知识。 |
| 5.2 | 监督微调 | Supervised Fine-Tuning，SFT | 使用人工或程序构造的标准输入—输出样本进行监督训练。 | 学习期望回答、任务格式和行为模式。 | 样本质量、覆盖范围和一致性决定微调效果。 |
| 5.3 | 参数高效微调 | Parameter-Efficient Fine-Tuning，PEFT | 只训练少量新增或选定参数的高效微调方法。 | 降低显存、计算和训练成本。 | 不是所有任务都能达到全量微调的效果。 |
| 5.4 | 低秩适配 | Low-Rank Adaptation，LoRA | 一种常见 PEFT 方法，通过低秩矩阵近似参数更新，而不完整更新全部模型参数。 | 低成本适配开源模型、特定任务或风格。 | 仍需要高质量训练集、验证集和回归评测。 |
| 5.5 | 基于人类反馈的强化学习 | Reinforcement Learning from Human Feedback，RLHF | 使用人类偏好数据、奖励模型和强化学习，使模型输出更符合人类偏好与安全要求。 | 通用模型对齐、风格偏好、安全行为优化。 | 主要用于模型训练与对齐，不是普通业务项目的默认首选方案。 |

### RAG 与微调对比

| 对比维度 | RAG | 微调 Fine-tuning |
|---|---|---|
| 主要改变什么 | 模型回答时获得的外部知识 | 模型的行为、任务能力或输出模式 |
| 适合的知识类型 | 私有、动态、经常变化、需要引用的知识 | 相对稳定的任务规律、格式、风格和行为 |
| 是否容易更新 | 更新知识源和索引即可 | 通常需要重新准备数据、训练和评测 |
| 是否便于引用 | 较适合，可保留来源 | 不擅长直接说明训练知识来源 |
| 典型用途 | 企业知识问答、政策查询、售后手册问答 | 分类、抽取、固定格式、语气和专业任务适配 |
| 主要风险 | 检索失败、错误版本、上下文噪声 | 训练数据偏差、能力退化、成本和维护复杂度 |
| 是否可以组合 | 可以 | 可以，但必须通过评测证明组合收益 |

## 6. Workflow、Agent 与工具调用

| 编号 | 概念 | 英文 / 缩写 | 定义 | 适用场景 | 关键边界或风险 |
|---|---|---|---|---|---|
| 6.1 | 工作流 | Workflow | 由预先定义的步骤、分支和规则组成的流程，执行路径大多可预测。 | 稳定、可审计、高风险、规则明确的业务过程。 | 灵活性较低，但可控性和可测试性更强。 |
| 6.2 | 智能体 | Agent | 模型根据目标、上下文和当前状态，动态决定下一步行动的系统。 | 多步骤任务、动态规划、工具选择和复杂信息处理。 | 自由度更高，同时带来更高的不确定性、成本和安全风险。 |
| 6.3 | 工具调用 | Tool Calling / Function Calling | 模型按照预定义接口生成工具名称和参数，由程序执行真实操作，再将结果返回模型。 | 查询实时数据、读取数据库、执行计算、创建工单、调用业务系统。 | 模型只负责选择和传参；程序必须校验权限、参数和执行结果。 |
| 6.4 | 智能体工作流 | Agentic Workflow | 在部分步骤中允许模型动态决策，但整体流程和边界仍受控制的系统。 | 既需要灵活判断，又要求可治理的生产场景。 | 通常比完全开放式 Agent 更容易审计、评测和上线。 |
| 6.5 | 记忆 | Memory | 为跨轮次或跨任务保留信息的机制。 | 短期对话状态、长期用户偏好、任务中间结果。 | 必须处理准确性、更新、遗忘、权限、隐私和错误记忆。 |

### Memory 类型

| 类型 | 定义 | 示例 | 主要风险 |
|---|---|---|---|
| 短期记忆 | 当前上下文中的对话状态 | 用户刚刚提供的型号和故障现象 | 超出上下文窗口后丢失 |
| 长期记忆 | 持久化保存的用户事实、偏好或历史记录 | 用户常用语言、设备列表、长期偏好 | 过期、错误、隐私和权限问题 |
| 工作记忆 | 执行任务时临时保存的中间结果 | Agent 已完成步骤、工具返回值、待办项 | 状态不一致或错误结果被继续使用 |

## 7. 评测核心定义

| 编号 | 概念 | 英文 / 缩写 | 定义 | 主要评测对象 | 使用注意事项 |
|---|---|---|---|---|---|
| 7.1 | 黄金评测集 | Golden Dataset | 经过人工审核、代表真实业务分布、包含预期结果和评分标准的固定评测集。 | 模型、Prompt、RAG、Agent 和系统版本对比。 | 必须覆盖正常、异常、边界、高风险和拒答场景。 |
| 7.2 | 基线方案 | Baseline | 用于比较的基础方案。 | 人工流程、关键词搜索、基础 Prompt、无重排 RAG。 | 没有 Baseline，就无法判断复杂方案是否真正改善效果。 |
| 7.3 | 准确率 | Accuracy | 预测正确样本数占总样本数的比例。 | 类别相对均衡、答案可明确判定的任务。 | 不适合直接代表开放式问答质量。 |
| 7.4 | 精确率 | Precision | 系统判定为正例的样本中，真正为正例的比例。 | 控制误报。 | 适合错误报警成本较高的场景。 |
| 7.5 | 召回率 | Recall | 所有真实正例中，被系统成功识别出的比例。 | 控制漏报。 | 适合漏掉问题成本较高的场景。 |
| 7.6 | F1 分数 | F1 Score | Precision 与 Recall 的调和平均。 | 同时平衡误报和漏报。 | 不能代替对不同错误成本的业务判断。 |
| 7.7 | 前 K 召回率 | Recall@K | 前 K 个检索结果中包含相关内容的查询比例。 | 检索系统是否召回正确证据。 | K 值应结合最终上下文容量和业务需求设定。 |
| 7.8 | 平均倒数排名 | Mean Reciprocal Rank，MRR | 根据第一个正确结果出现的位置计算平均倒数排名。 | 正确结果是否排在靠前位置。 | 主要关注第一个相关结果，对多个相关结果覆盖不充分。 |
| 7.9 | 上下文精确度 | Context Precision | 检索上下文中真正相关内容所占的程度。 | 返回结果是否包含过多噪声。 | 高召回不等于高精确，需要平衡覆盖和噪声。 |
| 7.10 | 忠实度 | Faithfulness | 生成答案中的陈述是否能由给定检索上下文支持。 | RAG 答案是否忠于证据。 | 忠于错误文档仍可能得到高分，因此还要检查知识正确性。 |
| 7.11 | 答案相关性 | Answer Relevance | 答案是否直接、完整地回应用户问题。 | 回答是否跑题、遗漏或冗余。 | 回答相关不代表事实一定正确。 |
| 7.12 | 事实依据性 | Groundedness | 回答是否建立在提供的事实、数据或工具结果之上，而不是自由发挥。 | 检索、工具调用和事实约束场景。 | 不同评测框架定义可能不同，使用时必须明确评分规则。 |
| 7.13 | 大模型裁判 | LLM-as-a-Judge | 使用大模型按照评分规则评价另一个模型的输出。 | 大规模自动评测。 | 可能存在位置偏差、措辞偏差和模型偏好，必须用人工样本校准。 |
| 7.14 | 人工评测 | Human Evaluation | 由领域专家或目标用户按照明确 Rubric 评价系统输出。 | 高风险、复杂、主观或专业任务。 | 成本较高，但在关键场景中不可替代。 |
| 7.15 | 任务成功率 | Task Success Rate | 用户任务最终成功完成的比例。 | 产品和业务结果。 | 比文本相似度更接近真实效果，需要定义“任务完成”的标准。 |
| 7.16 | 自动解决率 | Containment Rate | 问题无需人工介入，由自动系统完整解决的比例。 | 客服、售后和服务自动化。 | 不能为了提高自动解决率而错误阻止人工升级。 |
| 7.17 | 人工升级率 | Escalation Rate | 需要升级到人工或更高级支持的比例。 | 自动化系统边界和人工负担。 | 应分别评估正确升级、错误升级和漏升级。 |

### Precision、Recall 的业务理解

| 业务关注 | 应重点关注的指标 | 示例 |
|---|---|---|
| 误报成本高 | Precision | 把正常设备误判为严重故障会产生不必要维修费用 |
| 漏报成本高 | Recall | 漏掉安全风险可能造成人身伤害或设备损坏 |
| 两者都重要 | F1 + 分项指标 | 售后故障分类既要减少误报，也不能漏掉真实故障 |

## 8. 生产工程与 LLMOps

| 编号 | 概念 | 英文 / 缩写 | 定义 | 主要用途 | 关键注意事项 |
|---|---|---|---|---|---|
| 8.1 | 大模型应用运维 | LLMOps | 围绕 LLM 应用的数据、Prompt、模型、评测、部署、监控和迭代进行管理的方法。 | 版本管理、持续评测、上线、监控和优化。 | 管理对象不只是模型，还包括数据、Prompt、检索、工具和评测集。 |
| 8.2 | 可观测性 | Observability | 使系统内部运行状态能够被观察和分析的能力。 | 记录请求链路、Prompt、检索结果、工具调用、Token、时延、错误和输出。 | 日志中可能包含隐私和敏感数据，需要脱敏与权限控制。 |
| 8.3 | 链路追踪 | Trace | 一次完整请求经过各组件的执行记录。 | 定位 RAG、Workflow 和 Agent 错误。 | 应保留每个步骤的输入、输出、版本、耗时和错误信息。 |
| 8.4 | 时延 | Latency | 从请求开始到响应完成所需的时间。 | 评估用户体验和系统性能。 | 应关注 P50、P95、P99，而不只看平均值。 |
| 8.5 | 吞吐量 | Throughput | 单位时间内系统能够处理的请求量。 | 容量规划、并发评估和成本分析。 | 吞吐量、时延、模型规模和成本之间通常需要权衡。 |
| 8.6 | 防护机制 | Guardrail | 用于约束输入、输出或执行行为的机制。 | 敏感信息检测、内容安全、结构校验、事实校验、权限校验、工具白名单。 | Guardrail 应多层设置，不能只依赖 Prompt。 |
| 8.7 | 降级策略 | Fallback | 主方案失败时使用的替代处理方式。 | 换模型、关键词搜索、返回引用、要求补充信息、转人工。 | 必须提前定义触发条件和用户提示，避免静默失败。 |
| 8.8 | 回归测试 | Regression Test | 系统更新后重新运行固定评测集，确认原有能力没有退化。 | 模型、Prompt、检索、数据和代码版本升级。 | 不仅检查平均分，还要检查关键案例和高风险案例。 |
| 8.9 | 总拥有成本 | Total Cost of Ownership，TCO | 系统全生命周期的总成本。 | 模型调用、向量数据库、开发、运维、评测、人工审核、数据治理、迁移成本。 | 不能只比较单次模型调用价格，应计算完整生命周期投入。 |

## 9. 方案选择速查表

| 问题特征 | 优先方案 | 选择原因 | 不建议的做法 |
|---|---|---|---|
| 规则明确、结果确定、风险高 | 规则引擎 / Workflow | 路径稳定、可测试、可审计 | 为了“智能化”强行使用开放式 Agent |
| 需要私有或实时知识、要求引用 | RAG | 可接入外部知识并保留来源 | 让模型凭训练记忆自由回答 |
| 固定分类、抽取、风格或格式 | Fine-tuning / 结构化 Prompt | 重点是行为和输出稳定 | 用 RAG 代替任务能力训练 |
| 需要查询实时系统或执行操作 | Tool Calling | 通过真实系统获得数据并完成动作 | 让模型虚构查询或操作结果 |
| 步骤稳定、审计要求高 | Workflow | 流程清晰、风险可控 | 让 Agent 自由决定所有步骤 |
| 路径无法预先穷举、需要动态决策 | 受控 Agent | 允许模型根据状态灵活选择下一步 | 使用无权限、无预算、无终止条件的开放 Agent |
| 文档知识变化，同时行为需要稳定 | RAG + Fine-tuning | 分别解决知识更新和行为适配 | 不经评测直接叠加多种复杂技术 |
| 简单任务即可解决 | Prompt / 规则 / 普通程序 | 成本低、稳定、易维护 | 增加不必要的 Agent 或复杂 RAG |

## 10. 产品经理必须能够回答的问题

| 场景 | 必须回答的问题 |
|---|---|
| 模型选型 | 为什么选择这个模型？与其他模型相比，质量、时延、成本和部署条件如何？ |
| RAG 方案 | 正确资料是否被召回？错误来自解析、分块、检索、重排还是生成？ |
| 准确率要求 | 准确率具体指检索召回、答案正确、忠于证据、任务成功还是业务指标？ |
| RAG 与微调 | 当前问题是知识不足，还是行为与任务能力不稳定？ |
| Agent 使用 | 为什么需要动态决策？Workflow 是否已经足够？ |
| 上线风险 | 什么情况下拒答、降级或转人工？高风险答案如何治理？ |
| 业务价值 | 系统改善了什么流程、指标和成本？是否优于当前 Baseline？ |
| 持续迭代 | 更新数据、Prompt、模型或检索后，如何进行回归测试？ |
