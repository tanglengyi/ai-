# 04｜AI 评测体系与 LLMOps

## 1. “准确率”不是一个完整指标

客户问“准确率多少”时，首先要确认：

- 是检索到正确资料的比例？
- 是答案与标准答案一致的比例？
- 是答案忠于资料的比例？
- 是正确拒答的比例？
- 是用户最终完成任务的比例？
- 是无需人工升级的比例？

开放式问答很难用单一 Accuracy 表达。生产系统应建立四层评测体系。

## 2. 四层评测模型

### 2.1 检索层

目标：正确证据是否被召回，并且排名足够靠前。

常见指标：

- Recall@K。
- Precision@K。
- MRR。
- NDCG。
- Context Precision。
- 元数据过滤正确率。

关键问题：

- 正确文档是否在 Top-K？
- 返回结果中有多少噪声？
- 正确版本是否优先？
- 型号、错误码和语言过滤是否正确？

### 2.2 生成层

目标：模型是否基于证据给出正确、相关、完整的答案。

常见指标：

- Faithfulness。
- Answer Correctness。
- Answer Relevance。
- Completeness。
- Citation Correctness。
- 格式合规率。

关键问题：

- 每个陈述是否有证据支持？
- 是否遗漏关键操作或风险提醒？
- 引用是否真的支持答案？
- 是否将“可能原因”表述成“确定结论”？

### 2.3 系统层

目标：完整系统在真实交互中的可靠性。

常见指标：

- 任务成功率。
- 正确拒答率。
- 追问有效率。
- 工具调用成功率。
- 人工升级准确率。
- P50/P95/P99 时延。
- 错误率与超时率。
- 单次任务 Token 和成本。

### 2.4 业务层

目标：AI 是否真正改变业务结果。

常见指标：

- 首次解决率。
- 平均处理时长。
- 人工升级率。
- 客服采纳率。
- 客户满意度。
- 重复来询率。
- 单工单成本。
- 错误建议造成的返工或风险事件。

## 3. Golden Dataset 建设

### 3.1 定义

Golden Dataset 是经过领域专家审核、覆盖真实业务分布、带有预期答案和评分规则的固定评测集。

### 3.2 数据来源

建议从以下来源抽样：

- 真实用户问题。
- 售后工单。
- 客服聊天记录。
- 搜索日志。
- 产品手册中的标准问题。
- 历史失败案例。
- 专家构造的边界和攻击样本。

必须进行授权和脱敏。

### 3.3 样本类型

至少覆盖：

1. 简单事实题。
2. 同义改写题。
3. 多条件判断题。
4. 多轮信息补充题。
5. 版本冲突题。
6. 文档中无答案的问题。
7. 应拒答的问题。
8. 应转人工的问题。
9. 用户错误描述或前提错误的问题。
10. 多语言问题。
11. Prompt Injection 或越权问题。
12. 长上下文和噪声问题。

### 3.4 建议字段

- case_id。
- language。
- scenario。
- user_query。
- conversation_context。
- product_model。
- firmware_version。
- expected_documents。
- expected_answer_points。
- forbidden_claims。
- expected_action。
- should_abstain。
- should_escalate。
- severity。
- evaluator_notes。

模板见：`templates/evaluation-dataset-template.csv`。

### 3.5 数据集拆分

- 开发集：调试 Prompt 和检索方案。
- 验证集：选择参数和方案。
- 测试集：最终报告，避免频繁查看导致过拟合。
- 生产回归集：由线上高频和高风险样本持续补充。

不要在同一批样本上反复调参后再宣称最终效果。

## 4. 评分 Rubric

开放式答案需要明确评分维度。例如每条答案按以下规则评分：

| 维度 | 0 分 | 1 分 | 2 分 |
|---|---|---|---|
| 事实正确 | 核心事实错误 | 部分正确 | 全部正确 |
| 证据忠实 | 大量无依据 | 少量推断 | 所有关键陈述有依据 |
| 完整性 | 漏关键步骤 | 次要遗漏 | 覆盖全部要点 |
| 相关性 | 偏题 | 有冗余 | 直接回应 |
| 风险处理 | 危险建议 | 提醒不足 | 正确拒答/升级 |
| 引用 | 无或错误 | 部分支持 | 引用准确完整 |

评分规则必须包含正例和反例，避免不同评审人员理解不一致。

## 5. 自动评测、人工评测与 LLM-as-a-Judge

### 5.1 确定性自动评测

适合：

- JSON 是否符合 Schema。
- 必填字段是否存在。
- 工具参数是否正确。
- 分类标签是否一致。
- 引用文档 ID 是否属于允许集合。
- 禁止词或敏感字段是否出现。

优点：稳定、快速、成本低。

### 5.2 LLM-as-a-Judge

适合：

- 语义正确性。
- 完整性。
- 回答相关性。
- 忠实度。
- 对比两个回答哪个更好。

风险：

- Judge 模型自身可能判断错误。
- 对答案长度、语言风格和位置存在偏差。
- 同一模型评价自己可能偏高。
- 评分 Prompt 改变会造成指标不可比。

使用要求：

- 固定 Judge 模型和版本。
- 固定评分 Prompt。
- 使用清晰 Rubric。
- 抽取一批样本与人工评分对齐。
- 保存 Judge 的理由，便于复核。

### 5.3 人工评测

高风险问题、领域专业问题和上线前验收必须保留人工评测。

建议记录：

- 评审人角色。
- 评分时间。
- 分数。
- 错误标签。
- 修改建议。
- 是否可上线。

### 5.4 组合方式

推荐：

```text
确定性规则检查
+ LLM 批量语义评测
+ 领域专家抽样复核
+ 线上用户行为指标
```

## 6. 错误分类体系

每个失败样本应标记根因，而不只是“回答错误”。

### 6.1 数据问题

- 知识缺失。
- 文档过期。
- 文档冲突。
- 数据未同步。
- 元数据错误。

### 6.2 解析与索引问题

- OCR/解析失败。
- 表格结构丢失。
- 分块切断语义。
- Embedding 或索引未更新。

### 6.3 查询与检索问题

- 用户问题存在歧义。
- Query Rewrite 错误。
- 过滤条件错误。
- 召回失败。
- 排名错误。

### 6.4 生成问题

- 忽略证据。
- 错误推断。
- 遗漏步骤。
- 格式不合规。
- 引用错误。

### 6.5 流程和工具问题

- 未追问必要信息。
- 工具选择错误。
- 工具参数错误。
- 未正确处理工具失败。
- 应转人工但未转。

### 6.6 业务定义问题

- 标准答案不完整。
- 业务规则未统一。
- 部门之间口径冲突。
- 目标指标不合理。

最后一类非常重要：有时不是模型不够好，而是企业自己没有统一标准答案。

## 7. 离线评测流程

```text
确定业务目标
→ 建立 Baseline
→ 构建 Golden Dataset
→ 定义指标和阈值
→ 运行候选方案
→ 错误归因
→ 只修改一个主要变量
→ 回归测试
→ 输出质量/成本/时延报告
```

建议每次实验记录：

- experiment_id。
- 日期和负责人。
- 数据集版本。
- 模型和版本。
- Prompt 版本。
- 索引版本。
- Chunk 参数。
- 检索参数。
- Reranker。
- 指标结果。
- 成本和时延。
- 失败样本列表。
- 结论与下一步。

## 8. 在线评测

### 8.1 灰度发布

先向少量内部用户或低风险流量开放，逐步扩大范围。

### 8.2 A/B Test

比较两个方案对真实业务指标的影响。应保证：

- 用户分组合理。
- 实验周期覆盖业务波动。
- 除被测变量外其他条件尽量一致。
- 不只比较点击或点赞，也比较任务是否成功。

### 8.3 隐式反馈

- 用户是否重新提问。
- 是否复制答案。
- 是否点击引用。
- 是否采纳建议。
- 是否转人工。
- 人工是否修改 AI 答案。
- 问题是否再次发生。

隐式反馈不能直接等同于答案正确，例如用户不追问可能是放弃使用。

## 9. 阈值设计

不同场景使用不同阈值。

示例：

| 场景 | 质量要求 | 策略 |
|---|---|---|
| 普通 FAQ | 中等 | 可直接回答并引用 |
| 故障排查 | 较高 | 缺信息先追问 |
| 安全相关 | 很高 | 证据不足必须转人工 |
| 内部内容草稿 | 中等 | 明确标记待审核 |
| 自动执行操作 | 很高 | 参数校验与二次确认 |

系统不应使用统一的“置信度 > 0.7 即回答”覆盖所有场景。

## 10. LLMOps 版本体系

生产中需要记录：

- 数据源版本。
- 文档版本。
- Parser 版本。
- Chunking 版本。
- Embedding 模型版本。
- 索引版本。
- 检索与重排配置。
- Prompt 版本。
- 模型版本。
- 工具 Schema 版本。
- 评测集与 Rubric 版本。

可将一次完整发布表示为：

```yaml
release: rag-support-v1.3.0
data_version: kb-2026-07-24
parser_version: parser-0.4.1
chunk_strategy: heading-parent-child-v2
embedding_model: xxx
retrieval: hybrid-rrf-top30
reranker: xxx-top5
prompt_version: answer-v1.8
llm_model: pinned-model-version
eval_dataset: support-golden-v1.2
```

## 11. 可观测性

每次请求建议记录：

- request_id 和用户/租户信息。
- 原始问题和改写问题。
- 元数据过滤条件。
- 召回文档及分数。
- 重排结果。
- 进入模型的上下文。
- Prompt 和模型版本。
- 模型输出。
- 工具调用和返回值。
- Token、时延和成本。
- 是否拒答/升级。
- 用户反馈和最终处理结果。

隐私场景下应进行脱敏、权限控制和保留周期管理。

## 12. 生产监控面板

### 质量

- 任务成功率。
- 正确拒答率。
- 引用有效率。
- 人工修改率。
- 高频失败问题。

### 性能

- P50/P95/P99 时延。
- 超时率。
- 工具失败率。
- 向量库查询时延。

### 成本

- 每次请求成本。
- 每个成功任务成本。
- 输入/输出 Token。
- 缓存命中率。
- 不同模型成本分布。

### 业务

- 首次解决率。
- 人工升级率。
- 平均处理时长。
- 客服采纳率。
- 满意度与投诉率。

## 13. 上线门槛示例

上线门槛必须根据实际风险制定。示例：

- 高风险问题正确升级率 ≥ 98%。
- 核心问题 Recall@5 ≥ 90%。
- Faithfulness ≥ 0.90。
- 引用准确率 ≥ 95%。
- 结构化输出合规率 ≥ 99%。
- P95 时延 ≤ 8 秒。
- 单次成功任务成本低于人工节省成本的 20%。
- 不允许出现跨租户数据泄露。

这些数字只是示例，不能直接作为所有项目标准。

## 14. 评测报告结构

1. 业务目标与范围。
2. Baseline。
3. 数据集构成和覆盖范围。
4. 评测方法与 Rubric。
5. 候选方案和实验变量。
6. 检索层结果。
7. 生成层结果。
8. 系统性能与成本。
9. 业务指标或试点结果。
10. 失败样本和根因分析。
11. 风险与限制。
12. 上线建议和下一步计划。

## 15. 核心原则

- 没有评测集，不做“优化”。
- 没有 Baseline，不证明“提升”。
- 只看平均分，会掩盖高风险失败。
- 自动评测不能完全替代领域专家。
- 线上点赞不能直接证明答案正确。
- 指标必须与业务决策关联。
- 每次变更都要可复现、可回滚、可比较。
